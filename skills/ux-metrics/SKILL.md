# UX Metrics

디자인이 사용자에게 실제로 도움이 됐는지 잴 수 있게 만든다. 지표는 목표에서 출발하고, 결과를 보기 전에 판단 규칙을 정한다.

## Trigger

- `@ux metrics <기능|화면>`: 지표 체계 설계
- `@ux experiment <가설>`: A/B 실험 계획
- 「성공 지표 정해 줘」, 「HEART로 정리」, 「이벤트 설계」, 「퍼널 정의」, 「SUS 점수 계산」

## Input

- `feature`: 기능과 사용자에게 주려는 변화
- `decision`: 측정 결과로 내릴 결정
- `users`: 대상과 제외할 사용자(직원·테스트 계정)
- `existing`: 이미 쌓이는 이벤트·대시보드
- `constraints`: 트래픽 규모, 기간, 동의·개인정보 제약

## Process

1. 목표를 먼저 쓴다. 잴 수 있는지는 아직 따지지 않는다. 사용자 목표와 사업 목표를 따로 적는다.
2. HEART 다섯 범주(Happiness·Engagement·Adoption·Retention·Task success)를 하나씩 넣거나 빼고, 뺀 이유를 적는다. 필수 업무 도구에서 사용 빈도는 성공이 아닐 수 있다.
3. 목표마다 신호를 고른다 — 목표가 움직일 때만 같이 움직이는 행동이나 태도다. 포기·되돌리기·오류·재시도·문의 같은 실패 신호가 더 정직한 경우가 많다.
4. 신호를 지표로 만든다. 분모, 기간, 집계 단위(사용자당 비율·평균)를 적는다. 원수(총 클릭 수)는 성공 지표로 쓰지 않는다.
5. 가드레일을 정한다 — 나빠지면 안 되는 지표(문의·환불 요청·삭제·오류율·응답 시간·접근성 문제). 해지율을 낮추는 실험에는 해지 관련 문의와 불만을 반드시 가드레일로 둔다.
6. 태도 지표가 필요하면 SUS나 단일 문항 만족도를 고르고, 점수 계산과 해석 기준을 [`references/heart-gsm.md`](./references/heart-gsm.md)에서 적는다.
7. 이벤트 명세를 쓴다 — 이름(snake_case), 발생 시점, 속성, 제외할 개인정보, 필요한 동의.
8. 실험이 필요하면 [`references/experiment-plan.md`](./references/experiment-plan.md) 양식으로 가설, 주 지표 하나, 가드레일, 최소 검출 효과와 필요한 표본, 기간(요일 효과를 덮는 온전한 주 단위), 멈춤 규칙, 미리 정한 세그먼트를 쓴다.
9. 결과를 보기 전에 판단 규칙을 쓴다 — 「주 지표가 +X 이상이고 가드레일이 모두 유지되면 출시, 아니면 …」. 실사용자가 거의 없어 필요한 표본에 닿지 못하면 A/B를 계획하지 않는다. 이벤트를 먼저 깔고, 비율을 관찰 지표로만 읽고, 판단 규칙은 「표본이 N명에 닿으면 적용」으로 미룬다.
10. 정성 결과와 함께 읽는다. 지표가 왜 움직였는지는 `ux-research`로 확인한다.

## Output

- 목표 → 신호 → 지표 표(HEART 범주별, 제외한 범주와 이유 포함)
- 가드레일 목록
- 이벤트 명세 표
- 실험 계획(해당 시)과 판단 규칙
- 판정: 아래 게이트를 모두 지나면 `READY`, 아니면 `NOT_READY`

## Hard Gates

| ID  | FAIL 조건                                            |
| --- | ---------------------------------------------------- |
| G1  | 지표에 분모나 기간이 없음                            |
| G2  | 원수(총 클릭·총 방문)를 성공 지표로 씀               |
| G3  | 가드레일이 없음                                      |
| G4  | 실험의 주 지표나 판단 규칙을 결과를 본 뒤에 정함     |
| G5  | 이벤트 속성에 이메일·전화번호 같은 개인정보가 들어감 |
| G6  | 데이터나 검정 없이 「유의미한 차이」를 주장함        |

## Skill Chaining

- 지표가 움직인 이유 확인: `ux-research`
- 이벤트를 화면 설계서에 넣기: `ux-spec`
- 유지율을 기만 없이 높이는지 점검: `ux-dark-patterns`
- 지표가 가리킨 화면의 문제 찾기: `ux-review`

## Constraints

- 표본이 작은 정성 결과를 비율 지표로 바꾸지 않는다.
- 결과를 본 뒤 세그먼트를 골라 유리한 숫자를 찾지 않는다.
- 사용자가 동의하지 않은 추적을 설계하지 않는다.
- 지표를 올리려고 사용자를 붙잡는 설계(해지 방해·반복 팝업)를 권하지 않는다.
