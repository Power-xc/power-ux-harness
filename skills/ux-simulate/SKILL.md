# UX Simulate

사용자를 만나기 전에 자료와 합성 페르소나로 후보안을 미리 걸러 낸다. 결과는 언제나 가설이고, 실제 사용자로 확인할 계획까지 내야 끝난다.

## Trigger

- `@ux simulate <결정|기능>`: 자료 조사 → 합성 페르소나 → 후보안 시뮬레이션 → 추천
- `@ux discover <도메인>`: 낯선 도메인을 조사해 결정할 것과 후보안부터 정리
- 「기획서랑 링크 줄 테니 어떤 UX가 맞을지 봐 줘」, 「가상 페르소나로 돌려 봐」, 「인터뷰 전에 안을 좁혀 줘」, 「A안 B안 중 뭐가 덜 막힐까」

## Input

- `domain`: 서비스 분야와 대상 사용자
- `links`: 우리 서비스·비슷한 서비스·앱 리뷰·규제 문서 주소
- `docs`: 기획서·요구사항·화면·데이터 파일
- `decision`: 정할 것 하나. 없으면 기획서에서 한 문장으로 뽑아 `가정`으로 적고 진행한다.
- `constraints`: 정책·기술·일정·법무 조건
- `data`(선택): 실제 인터뷰·설문·문의 기록, 인구 데이터셋

## Process

1. 결정 문장 하나와 판단 기준을 먼저 적는다. 기준의 가중치는 결과를 보기 전에 정한다.
2. 받은 링크와 문서를 모두 연다. 열지 못한 것은 `NOT_CHECKED`로 남기고 내용을 짐작하지 않는다. 연 자료마다 출처 ID(`S1`…)를 붙인다.
3. 데스크 리서치 — 해당 분야 규제와 가이드라인, 비슷한 서비스의 흐름을 단계·패턴으로 분해, 앱 리뷰를 기간·건수·분류 기준과 함께 센다. 절차와 양식은 [`references/desk-research.md`](./references/desk-research.md). 비슷한 서비스 흐름 분해가 깊어지면 `ux-benchmark`로 넘긴다.
4. 페르소나 3~5명을 만든다. 실제 데이터나 인구 데이터의 구조화된 속성에서 먼저 뽑고 쿼터와 seed를 적는다. 속성마다 출처 ID나 `가정`을 단다. 접근성·경계 페르소나와 회의적 페르소나를 1명씩 꼭 넣고(접근성 조건은 서술만 주지 말고 그 조건으로 렌더한 캡처를 함께 준다), 기준선으로 빈 페르소나와 인구통계만 있는 페르소나를 함께 돌린다. 규칙은 [`references/persona-protocol.md`](./references/persona-protocol.md). `ux-benchmark`의 맥락 카드가 있으면 속성을 거기서 가져온다.
5. 후보안 2~3개를 패턴 이름·상태·문구 수준으로 쓴다. 후보 설명은 같은 틀에 장점·단점을 같은 수로 적고, 한 후보에서 여러 요소를 한꺼번에 바꾸지 않는다. 결함을 일부러 넣은 미끼 안 하나를 섞되 페르소나에게 알리지 않는다.
6. 페르소나 × 후보안마다 핵심 과제를 단계로 나누고 인지적 워크스루 4문항을 묻는다. 지금까지의 화면 이력을 맥락에 두고, 평가보다 자유 서술과 반대 의견을 먼저 받는다. 가능하면 페르소나마다 독립된 서브에이전트로 돌리고 가설과 평가 중이라는 사실을 숨긴다. 후보를 나란히 보여야 하는 비교 과제는 숨길 수 없으므로, 첫인상은 후보 하나만 보여 주는 단일안 실행으로 따로 받는다.
7. 후보안 순서와 이름표(순서가 없는 기호, 답에 그대로 쓰게 지시)를 바꿔 기본 3회 실행한다. 결정이 크면 5회, 가능하면 다른 모델 계열로 1회 더 돌린다. 모델·버전·프롬프트·설정·날짜를 기록한다. 절차는 [`references/simulation-protocol.md`](./references/simulation-protocol.md).
8. 유효성을 확인한다. 미끼는 순위와 따로 예/아니요 질문으로도 확인하고, 미끼를 통과시킨 실행과 이름표를 바꿔 쓴 답은 버린다. 기준선과 결과가 같으면 「페르소나 신호 없음」으로 적고, 근거 사슬에서 페르소나 속성을 빼고 후보 문구 차이로 설명한다. 답이 몇 가지로 몰리면 고유 답 수와 함께 적는다.
9. 순위와 안정성으로만 판단한다(예: 3회 모두 B안 1위). 비율·효과 크기·「사용자의 N%」를 쓰지 않는다. 추천마다 근거 사슬(출처 → 페르소나 속성 → 막힌 단계 → 판단)을 붙인다.
10. 추천안을 기만 패턴 기준으로 다시 보고, 이 시뮬레이션이 볼 수 없는 것을 적는다 — 드문 답, 작은 세그먼트, 감정, 실제 행동, 국내 사용자 대표성.
11. 검증 계획을 쓴다 — 가장 위험한 가설 3개, 실제 사용자 방법과 인원(라운드당 5명), 볼 지표, 추천을 뒤집을 결과.

## Output

첫 줄은 언제나 「합성 시뮬레이션 — 가설이며 사용자 증거가 아니에요」.

1. 결정 문장과 판단 기준(가중치)
2. 출처 표: ID, 종류, 제목·주소, 연 날짜, 쓴 곳
3. 데스크 리서치 요약: 규제, 흐름 분해, 리뷰 분류(기간·건수)
4. 페르소나 카드: 속성 | 값 | 근거(출처 ID·`가정`)
5. 후보안: 패턴 이름·상태·문구
6. 워크스루 표: 페르소나 × 후보안의 실패 단계와 실패 이야기
7. 반복 결과: 실행별 순위, 일치율, 기준선 비교, 미끼 안 결과
8. 추천과 근거 사슬, 볼 수 없는 것
9. 검증 계획
10. 판정: `READY | NOT_READY | BLOCKED` — READY는 추천과 검증 계획을 실제 사용자 리서치로 넘길 수 있는 상태

## Hard Gates

| ID  | FAIL 조건                                                                   |
| --- | --------------------------------------------------------------------------- |
| G1  | 열지 않은 자료를 인용하거나, 출처 ID도 `가정`도 없는 주장이 있음            |
| G2  | 합성 결과를 사용자 증거처럼 쓰거나 비율·효과 크기로 보고함                  |
| G3  | 후보안이 2개 미만이거나, 미끼 안 없이 실행하거나, 미끼를 통과시킨 실행을 씀 |
| G4  | 접근성·경계 페르소나나 회의적 페르소나가 없음                               |
| G5  | 순서를 바꾼 반복 실행이나 기준선 비교 없이 추천함                           |
| G6  | 검증 계획에 가장 위험한 가설·실제 사용자 방법·뒤집을 결과가 없음            |
| G7  | 추천안에 기만 패턴이 있음                                                   |

## Skill Chaining

- 실제 사용자로 검증할 인터뷰·사용성 테스트: `ux-research`
- 같은 상황을 푼 다른 서비스 사례를 깊게 조사하고 맥락별 안 제안: `ux-benchmark`
- 추천안의 흐름과 화면 목록: `ux-flow`
- 화면 설계서: `ux-spec`
- 규제와 기만 패턴 확인: `ux-dark-patterns`
- 검증 지표와 실험: `ux-metrics`
- 후보안의 문구: `ux-writing`

## Constraints

- 합성 결과를 「사용자 리서치」라고 부르지 않는다.
- 실제 인물의 이름·연락처·민감 정보를 페르소나에 넣지 않는다. 리뷰 인용은 작성자 없이 짧게 쓴다.
- 비슷한 서비스의 화면을 그대로 옮긴 안을 내지 않는다. 흐름과 패턴 수준으로만 가져온다.
- 로그인 벽이나 유료 자료를 우회해서 가져오지 않는다. 유료 API는 사용자가 허락한 경우에만 쓴다.
- 고정관념으로 페르소나를 그리지 않는다. 집단 이름표보다 과제와 상황으로 페르소나를 정의한다.
