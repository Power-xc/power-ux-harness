# UX Spec

개발자나 코딩 에이전트가 다시 묻지 않고 만들 수 있는 화면 설계서를 쓴다. 기준은 하나다 — 읽는 사람마다 같은 화면이 나와야 한다.

## Trigger

- `@ux spec <화면 ID|화면명>`: 화면 한 장 또는 여러 장의 설계서
- 「화면설계서 써 줘」, 「스토리보드 정리해 줘」, 「개발에 넘길 스펙」, 「에이전트가 구현할 화면 명세」
- 리뷰 결과나 흐름도를 구현 가능한 명세로 옮기는 요청

## Input

- `screens`: 화면 ID와 화면명(가능하면 `ux-flow`의 화면 목록)
- `goal`: 화면마다 사용자가 하는 일
- `design_system`: 쓰는 디자인 시스템과 컴포넌트 이름(없으면 표준 이름)
- `content`: 정해진 문구·데이터·정책
- `figma`: 프레임 링크나 스크린샷(있으면)

화면 목록이 없으면 먼저 `ux-flow`로 화면 ID를 정한다. 정책이 비어 있으면 지어내지 않고 「정해야 할 것」에 올린다.

## Process

1. 문서 머리에 프로젝트·버전·날짜·작성자와 개정 이력을 한 번만 둔다. 화면마다 반복하지 않는다.
2. 화면마다 화면 ID, 경로, 목적(한 문장), 진입(어디서 오는가)과 이탈(어디로 가는가)을 쓴다.
3. 화면을 영역으로 나누고 번호(①②③)를 붙인다. 와이어프레임이나 프레임 링크의 번호와 설명 표의 번호를 맞춘다.
4. 영역마다 [`references/component-names.md`](./references/component-names.md)의 표준 이름으로 컴포넌트를 적는다. 「팝업」·「알림창」처럼 여러 패턴을 가리키는 말은 대화상자·바텀시트·토스트·스낵바 중 하나로 정한다.
5. 영역마다 동작(누르기·길게 누르기·밀기 → 결과), 상태별 모습(기본·누름·포커스·비활성·로딩·오류), 문구 초안(해요체, 실제 문장), 데이터(출처·형식·빈 값일 때)를 쓴다. 문구 규칙은 `ux-writing`을 따른다.
6. 화면 상태(빈 상태·로딩·오류·성공·권한 없음·끝)를 화면 단위로 따로 적는다. 패턴 선택은 [`../ux-review/references/pattern-fit.md`](../ux-review/references/pattern-fit.md)와 맞춘다 — 로딩은 기다림 길이로, 알림은 방해 수준으로 고른다.
7. 모션은 이름·시간·곡선으로 쓴다(예: 「바텀시트 등장 250ms 이즈 아웃, 닫힘 200ms」). 움직임 줄이기 설정에서의 대체를 적는다.
8. 접근성 메모를 쓴다 — 포커스 순서, 열릴 때와 닫힐 때 포커스가 갈 곳, 아이콘 버튼의 이름, 터치 영역 크기, 상태 메시지 알림 방식. 기준은 `ux-a11y`를 따른다.
9. 분석 이벤트를 쓴다 — 이벤트 이름(snake_case), 발생 시점, 속성. 이 화면의 성공을 잴 지표와 연결한다.
10. 예외를 쓴다 — 아주 긴 글자, 항목 0·1·많음, 느린 네트워크, 오프라인, 권한 거부, 두 번 누르기, 숫자·날짜·통화 형식.
11. 화면마다 완료 조건(acceptance criteria)을 관찰 가능한 문장으로 쓴다.
12. [`references/spec-template.md`](./references/spec-template.md)의 핸드오프 점검표로 마무리한다.

## Output

- 설계서 마크다운: 머리(버전·개정 이력) → 화면별 섹션(화면 ID·경로·목적·진입/이탈·영역 표·상태·모션·접근성·이벤트·예외·완료 조건) → 정해야 할 것
- 핸드오프 점검표 결과: 항목별 `PASS`·`FAIL`·`N/A`
- 판정: 게이트를 모두 지나면 `READY`, 아니면 `NOT_READY`와 빠진 항목

## Hard Gates

| ID  | FAIL 조건                                                     |
| --- | ------------------------------------------------------------- |
| G1  | 컴포넌트를 표준 이름 없이 「팝업」·「알림」처럼 모호하게 적음 |
| G2  | 동작에 결과 화면이나 상태가 없음                              |
| G3  | 문구가 「추후 작성」·「문구 필요」로 비어 있음                |
| G4  | 적용되는 화면 상태(빈·로딩·오류·끝)를 빠뜨림                  |
| G5  | 누를 수 있는 요소에 접근성 메모(이름·포커스·크기)가 없음      |
| G6  | 화면에 완료 조건이 없음                                       |
| G7  | 정해지지 않은 정책을 사실처럼 적음                            |

## Skill Chaining

- 화면 목록·흐름·상태 표: `ux-flow`
- 문구 다듬기와 점검: `ux-writing`
- 접근성 기준 확인: `ux-a11y`
- 맥락(연령·환경·예외)별 안과 다른 서비스 사례: `ux-benchmark`
- 패턴 쓰임이 맞는지 점검: `ux-review`
- 이벤트를 지표로 연결: `ux-metrics`
- AI 응답 화면이 포함되면 신뢰·통제 패턴: `ux-ai`
- 결제·구독·동의 화면이면 기만 패턴 점검: `ux-dark-patterns`

## Constraints

- 화면에 보이는 것만 쓰지 않는다. 보이지 않는 동작(데이터 호출·검증·권한)은 설명 칸에 쓴다.
- 디자인 시스템에 있는 컴포넌트를 새 이름으로 다시 정의하지 않는다.
- 색·간격 값을 숫자로 박지 않고 디자인 토큰 이름으로 쓴다(토큰이 있을 때).
- 실제 사용자 데이터를 예시 데이터로 쓰지 않는다.
- 한 화면 설계서를 기능 전체의 결정 문서로 부풀리지 않는다.
