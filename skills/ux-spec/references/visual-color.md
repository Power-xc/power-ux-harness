# 색 체계와 토큰

출처: jakubkrehel/skills(커밋 6c21201, MIT, Copyright (c) 2026 Jakub Krehel)의 `better-colors` — SKILL.md, palette-structure.md, token-naming.md, color-usage.md, contrast.md, palette-generation.md, color-formats.md. 원문 문장을 복사하지 않고 이 하네스의 절차에 맞게 다시 썼다. 값은 원본과 같다. 12절의 금융 색 항목은 이 하네스가 한국어 화면 기준으로 더했다.

설계서에서 색 체계와 토큰 이름을 정할 때(`ux-spec`)와 만든 화면의 색을 점검할 때(`ux-review`) 같은 문서를 기준으로 쓴다. 대비를 통과해야 하는지와 기준 수치(4.5:1, 3:1)는 [`../../ux-a11y/references/wcag22-checklist.md`](../../ux-a11y/references/wcag22-checklist.md)가 정하고, 픽셀로 재는 도구는 [`../../ux-a11y/scripts/contrast-from-pixels.mjs`](../../ux-a11y/scripts/contrast-from-pixels.mjs)다. 표면·그림자·아이콘 색은 [`visual-surface-motion.md`](./visual-surface-motion.md), 글자는 [`visual-type.md`](./visual-type.md)가 맡는다.

판정 원칙:

- 잰 적 없는 대비 값을 쓰지 않는다. 계산할 수 있는 색을 눈대중으로 정하지 않는다.
- 표기법(hex·`rgb()`·`oklch()`), 회색의 색조, 그라데이션의 보간 공간은 프로젝트의 선택이라 finding이 아니다.
- 역할 연결이 깨진 것, 대비에 실패한 짝, 색역 밖 단계는 finding이다.
- 같은 일을 프로젝트 안에서 두 방식으로 하면 finding이다. 프로젝트의 토큰이 있으면 그것을 먼저 쓴다.
- 이 문서에서 밝기는 OKLCH의 `L`(0\~1)이다.

## 1. 프로젝트 표기법을 따른다

프로젝트의 토큰과 표기법을 쓴다. 전부 hex인 체계가 hex에 `oklch()`를 섞은 체계보다 낫다.

새 체계는 `oklch()`를 기본으로 한다. 숫자가 아래 규칙대로 움직이기 때문이다. 그 밖에는 색 라이브러리로 같은 단계를 프로젝트 표기법으로 만든다(6절).

## 2. 체계는 단계 묶음이다

대부분의 제품에 필요한 묶음은 아래가 전부다.

| 묶음 | 개수 | 비고                                                                             |
| ---- | ---- | -------------------------------------------------------------------------------- |
| 무채 | 1    | 화면의 80\~90%(배경·테두리·본문 글자)를 맡는다                                   |
| 강조 | 1    | 브랜드 색조. 누를 수 있는 것과 선택된 상태                                       |
| 상태 | 0\~4 | `danger`·`warning`·`success`·`info`. 제품이 그 상태를 보여 줄 때만 하나씩 더한다 |

- 아무도 쓰지 않는 상태 묶음(예: 어디서도 불러 쓰지 않는 `warning`)은 유지비만 든다.
- 두 번째 강조 색조는 두 가지를 한눈에 구분해야 할 때만 둔다. 아니면 강조 한 묶음의 단계를 더 쓴다.

## 3. 단계마다 역할이 있다

묶음은 눈으로 고르는 그라데이션이 아니다. 단계는 역할이 필요로 해서 존재한다. 어떤 역할도 쓰지 않는 단계는 만들지 않는다.

| 역할               | Tailwind | Radix |
| ------------------ | -------- | ----- |
| 페이지 배경        | `50`     | `1`   |
| 옅은 배경          | `50`     | `2`   |
| 컴포넌트 배경      | `100`    | `3`   |
| 컴포넌트 호버      | `200`    | `4`   |
| 컴포넌트 눌림·선택 | `200`    | `5`   |
| 옅은 테두리·구분선 | `200`    | `6`   |
| 테두리·포커스 링   | `300`    | `7`   |
| 호버한 테두리      | `400`    | `8`   |
| 채움(solid)        | `600`    | `9`   |
| 채움 호버          | `700`    | `10`  |
| 낮은 대비 글자     | `700`    | `11`  |
| 높은 대비 글자     | `900`    | `12`  |

두 체계는 번호뿐 아니라 정의 방식도 다르다.

- Radix는 12단계를 역할로 정의한다. 9단계는 모든 묶음·모드에서 채움이다. 어두운 모드는 같은 번호를 쓰는 별도 묶음이라 `--accent-9`가 어느 모드에서나 채움이고 컴포넌트 CSS는 바뀌지 않는다.
- Tailwind는 11단계를 밝기로 정의한다. `50`이 밝고 `950`이 어둡다. 위 표의 대응은 밝은 모드에서 맞고 어두운 모드에서는 뒤집힌다(페이지 배경이 `950`, 높은 대비 글자가 `50`). 컴포넌트가 모드별로 단계 번호를 바꾸거나 한 번 바뀌는 의미 토큰을 읽는다.

프로젝트가 쓰는 쪽을 따른다. 새 체계는 역할 기준(Radix 식)이 테마가 바뀔 때 더 안전하다. Tailwind에서는 `50`\~`950`을 두고 역할 대응을 의미 층(7절)에 둔다.

- 채움이 `600`인 이유: 흰 글자가 대부분의 Tailwind `500` 색조에서 4.5:1에 못 미친다.
- 표에서 같은 단계가 반복되는 역할은 같게 보인다. 컴포넌트 호버와 옅은 테두리를 다르게 보이려면 12단계 묶음이 필요하다.

## 4. 무채색과 상태색

무채색:

- 순회색 묶음이 기본으로 충분하다. 어떤 강조 색조 밑에서도 경쟁하지 않고 브랜드 색이 바뀌어도 다시 볼 필요가 없다.
- 강조 색조로 기울이는 것은 스타일 선택이지 교정이 아니다. 강조 색조의 OKLCH chroma `0.005`\~`0.02`면 재어서 알 정도, 이름 붙일 정도는 아니다.
- 따뜻한 회색(주황 쪽)은 편안하고 편집물 같고, 차가운 회색(파랑 쪽)은 기술적이고 정밀하다. 어느 쪽이든(기울이지 않는 것 포함) 묶음 전체에서 한 방향을 유지한다. 차가운 배경에 따뜻한 테두리는 이름을 못 붙여도 보인다.
- 무채색이 가장 많은 역할을 맡으므로 단계가 가장 많아야 한다. 무채 단계 수는 강조 단계 수 이상이다.

상태색:

- 관례가 취향보다 먼저 상태 색조를 정한다. 빨강은 위험, 호박색은 경고, 초록은 성공이다. 문화 차이는 12절.
- 모든 상태 색조는 강조 색조에서 OKLCH 색조 `15°` 이상 떨어뜨린다. 브랜드가 빨강이면 위험도 빨강일 수 없다. 색조를 더 벌릴 수 없으면 파괴 동작을 외곽선 버튼에 아이콘을 붙이는 식으로 다르게 처리한다. 아니면 주요 행동으로 읽힌다.
- 상태 묶음은 강조보다 단계가 적다. 대부분은 배경·테두리·채움·글자 네 역할을 그린다. 상태 컴포넌트를 전 범위에 걸쳐 꾸밀 때만 전체 묶음을 만든다.

## 5. 단계 만들기

브랜드 색은 값 하나(대개 hex)로 온다. 묶음을 만들기 전에 둘을 정한다.

- 어느 단계를 차지하는가: 버튼·링크용 브랜드 색은 채움 단계(Tailwind `600`, Radix `9`)에 둔다. 그러면 주요 버튼이 브랜드 색 그대로 나온다.
- 고정인가 맞추는가: 계약상 고정인 브랜드 색은 고정한다(묶음이 그 점에서 바깥으로 자라고 그 한 칸 간격이 조금 어긋난다). 아니면 묶음에 맞춰 단계 간격을 규칙적으로 둔다.

브랜드 색이 흰 글자 뒤에서 대비에 실패해도 브랜드 색이다. 채움 단계에는 두지 않고 떨어진 자리에 두며, 누르는 채움에는 더 어두운 단계를 쓴다. 브랜드 색을 몰래 어둡게 하지 않는다. 예: `#3b82f6`은 `500`에 떨어지고 채움은 `600`을 쓴다. 흰색 위 `#3b82f6`은 3.68:1이다.

올바른 묶음의 성질(어떤 표기법의 결과든 확인할 수 있다):

- 밝기가 고르게 변한다. 측정은 OKLCH `L`로 한다. HSL 밝기는 지각 기준이 아니어서 값이 한쪽에 몰린다.
- 색조는 끝에서 끝까지 같다. 색조가 흔들리면 두 색을 섞은 것으로 읽히고 다른 색조의 무채 묶음 옆에서 어긋난다.
- 채도는 가운데에서 정점이고 양 끝에서 떨어진다. 가장 밝은 끝과 어두운 끝은 거의 무채색이고 가운데가 색을 나른다. 끝까지 채도를 두면 `50`이 번쩍이고 `950`이 번진 잉크 같다.
- 밝은 끝이 더 촘촘하다. `50`\~`200`은 OKLCH `L` 기준 `0.04`\~`0.05` 간격, 가운데 단계는 `0.07`\~`0.10` 간격이다. 전 범위를 고르게 나누면 옅은 단계가 모자라 `100`부터 이미 옅은 면으로 어둡다.
- 인접한 두 단계가 구분되지 않으면 안 된다. 인접 단계의 `L` 차가 `0.03` 미만이면 결정보다 단계가 많은 것이므로 하나를 뺀다.
- 양 끝은 순검정·순흰색에 닿지 않는다. 닿으면 페이지 배경이 있는 자리에서 정체성을 잃는다.

색 라이브러리를 쓴다. 손이나 눈으로 계산하지 않는다. `culori`·`colorjs.io`·`chroma.js`는 표기법 변환·지각 밝기 측정·지각 보간을 한다. 브랜드 색을 받은 형식으로 읽고 지각 공간에서 계산해 프로젝트 표기법으로 낸다.

```js
import { formatHex, interpolate, samples } from "culori";

// 지각 보간, hex 입력과 hex 출력
const ramp = interpolate(["#eff6ff", "#3b82f6", "#172554"], "oklab");
const steps = samples(11).map((t) => formatHex(ramp(t)));
```

이것은 시작점이다. 선형 샘플링은 각 구간 안에서 밝기를 고르게 나누므로 결과를 위 성질과 맞춰 보고 `50`\~`200`을 손으로 조인다. 출력 표기법은 프로젝트가 고르지만 묶음의 보간 공간은 고를 수 없다(sRGB 보간은 가운데 단계가 탁하다). 장식 그라데이션은 반대로 보간 공간이 의도한 모양이다(8절).

비교용 Tailwind 파랑은 밝은 끝이 더 촘촘하다.

```css
:root {
  --blue-50: #eff6ff;
  --blue-100: #dbeafe;
  --blue-200: #bfdbfe;
  --blue-300: #93c5fd;
  --blue-400: #60a5fa;
  --blue-500: #3b82f6;
  --blue-600: #2563eb;
  --blue-700: #1d4ed8;
  --blue-800: #1e40af;
  --blue-900: #1e3a8a;
  --blue-950: #172554;
}
```

색조가 여럿일 때(강조 + 상태) 묶음이 단계마다 일치해야 한다. `red-500`과 `blue-500`이 같은 밝기·선명도로 읽혀야 한다. 아니면 같은 단계에서 빨강 버튼이 파랑보다 무거워 보인다.

- 지각 밝기를 정확히 맞춘다. 같은 단계는 모든 색조에서 같은 밝기다.
- 선명도는 절대값 대신 비율로 맞춘다. 색조마다 최대 선명도가 다르다. 각 묶음을 자기 색조가 닿는 범위의 같은 비율로 둔다. 노랑과 청록은 정점이 빨강·파랑보다 훨씬 낮은 경우가 많다. 숫자를 그대로 복사하면 경고 색이 위험 색 옆에서 약해 보인다.

## 6. 표기법과 색역

| 표기법    | 좋은 점                                     | 약점                                                                      |
| --------- | ------------------------------------------- | ------------------------------------------------------------------------- |
| hex       | 어디서나 되고 간결하고 디자인 도구가 내준다 | 불투명. 채널을 손으로 읽거나 고칠 수 없다                                 |
| `rgb()`   | hex와 같은 범위, 알파 가독성                | 채널이 디자이너가 생각하는 것과 대응하지 않는다                           |
| `hsl()`   | 채널이 디자인 컨트롤처럼 보인다             | 밝기가 지각 기준이 아니고 색조가 흐른다. 밝기만 바꾼 묶음은 한쪽에 몰린다 |
| `oklch()` | 지각 균일 밝기, 안정된 색조, 예측되는 묶음  | Baseline 2023이라 아주 오래된 브라우저 범위는 대체가 필요하다             |

```css
oklch(L C H)          /* 밝기 0–1, chroma 0–~0.4, 색조 0–360 */
oklch(L C H / alpha)  /* 알파는 쉼표 대신 슬래시 */
```

변환은 사용자가 요청할 때, 합의된 이전이 범위에 있을 때, 프로젝트가 한 표기법으로 통일 중이고 이 값이 남은 하나일 때만 한다. 의도적으로 다른 표기법을 쓰는 프로젝트의 값 하나를 바꾸지 않는다. 변환할 때는 값만 바꾼다.

- `currentColor`·`inherit`·`transparent`·`initial`·`unset` 같은 키워드는 그대로 둔다.
- 그라데이션 함수는 그대로 두고 안의 색 정지점만 변환한다. 보간 방식은 건드리지 않는다.
- 특정 형식을 기대하는 외부 설정의 색은 그대로 둔다.
- 주석과 서식을 보존한다.

```css
/* 전 */
color: #3b82f6;
border: 1px solid rgba(0, 0, 0, 0.1);

/* 후 */
color: oklch(0.623 0.188 259.815);
border: 1px solid oklch(0 0 0 / 0.1);
```

일괄 변환은 정리가 아니고 이전이다. 모든 색이 반올림만큼 달라지고 요청하지 않은 파일이 바뀌므로 과제 자체여야 한다.

색역:

- 모든 sRGB 색은 Display P3에 있고 그 반대는 아니다. 추가 범위는 높은 chroma에만 있고 색조마다 다르다. OKLCH `L` `0.65`에서 초록은 chroma 약 `0.07`, 파랑은 약 `0.015` 늘어난다.
- 디스플레이가 못 내는 선명도는 색역 매핑되고 현재 브라우저에서는 대개 잘린다. 인접한 단계들이 한 색으로 뭉개져 sRGB 화면에서 묶음 끝의 구분이 사라진다. 최대 선명도는 색조와 밝기마다 달라서 청록은 빨강·보라보다 훨씬 낮은 곳에서 잘리고, 묶음의 어떤 단계는 잘리고 어떤 단계는 안 잘린다.
- 해결은 색조와 밝기를 두고 선명도를 낮추는 것이다. 디스플레이가 제한된 제품이 아니면 sRGB 기준으로 묶음을 만들고 P3는 향상으로 더한다. sRGB 값이 먼저 와야 sRGB 화면이 브라우저가 자른 색 대신 고른 색을 보여 준다.

```css
.success {
  background: #11ad32; /* oklch(0.65 0.2 145), sRGB 안 */
}

@media (color-gamut: p3) {
  .success {
    background: oklch(0.65 0.27 145);
  }
}
```

`oklch()` 이전 브라우저 범위는 같은 방식으로 `@supports`를 쓴다. 프로젝트의 실제 브라우저 범위를 확인하고, 최신 기준에서는 쓸모없는 코드다.

```css
.accent {
  background: #3b82f6;
}

@supports (color: oklch(0 0 0)) {
  .accent {
    background: oklch(0.623 0.188 259.815);
  }
}
```

알아 둘 최신 CSS: `color-mix()`(`color-mix(in oklab, var(--color-accent-solid) 15%, white)`처럼 옅은 배경을 만든다. 만들어 낸 값은 디자인 도구에서 못 보므로 토큰 층에 넣지 않는다), 상대 색 문법(`oklch(from var(--color-accent-solid) calc(l - 0.1) c h)`. 파생 셋이 이어지면 읽을 수 없다), `light-dark()`(두 모드 값을 한 선언에, 9절). 셋 다 렌더 때 풀리므로 대비를 보고하기 전에 풀린 값을 색 라이브러리로 계산하거나 렌더 결과를 잰다.

## 7. 토큰: 두 층과 이름

두 층:

- 원시(primitive): 값 이름이다. 색조와 단계로 `--blue-600`·`--neutral-200`처럼 쓴다. 테마가 바뀌어도 뜻이 바뀌지 않고 컴포넌트에서 직접 쓰지 않는다.
- 의미(semantic): 일 이름이다. 원시를 가리키고 맡은 역할 이름을 가진다(`--color-text-secondary`·`--color-border-subtle`). 컴포넌트는 이 층만 쓴다.

```css
:root {
  /* 1층: 원시, 색조와 단계 이름. 직접 쓰지 않는다. */
  --blue-600: #2563eb;
  --neutral-200: #e5e7eb;
  --neutral-700: #374151;

  /* 2층: 의미, 역할 이름. 컴포넌트가 쓴다. */
  --color-accent-solid: var(--blue-600);
  --color-border: var(--neutral-200);
  --color-text-secondary: var(--neutral-700);
}
```

- 테마는 의미 층만 다시 가리킨다. 어두운 모드·화이트라벨 테마·고대비 변형이 원시와 모든 컴포넌트를 건드리지 않는다. 컴포넌트가 `--blue-600`을 직접 쓰면 테마 이음매가 없고, 나중에 더하려면 어느 쓰임이 「강조」이고 어느 것이 「그냥 파랑」인지 전수 확인해야 한다.
- 컴포넌트 층(`--color-button-danger-bg`)은 컴포넌트가 의도적으로 체계와 달라야 할 때만 하나씩 둔다. 하나는 문서화된 예외이고, 스무 개면 의미 층에 역할이 빠진 것이다.

역할 목록: 아래 역할마다 토큰이 있으면 체계가 완성이다. 화면이 요구하는 순서대로 토큰을 더하면 먼저 만든 화면 모양의 팔레트가 된다.

| 묶음 | 역할                                                                         |
| ---- | ---------------------------------------------------------------------------- |
| 면   | 페이지 배경, 표면, 띄운 면(메뉴·팝오버), 꺼진 면(입력·우물), 오버레이 스크림 |
| 글자 | 기본, 보조, 비활성, 반전, 강조 위 글자(on-accent)                            |
| 선   | 옅은 선, 기본, 강한 선, 포커스 링, 구분선                                    |
| 강조 | 옅은 배경, 테두리, 채움, 채움 호버, 글자                                     |
| 상태 | 제품이 보여 주는 상태마다: 옅은 배경, 테두리, 채움, 글자                     |

구분선(separator)과 테두리(border)는 오늘 값이 같아도 다른 역할이다. 구분선은 내용을 나누고 테두리는 컨트롤을 감싼다. 입력 모양을 바꾸는 순간 둘이 갈라지는데, 하나로 합친 체계는 그때 풀어야 한다.

이름 문법: 한 꼴만 쓴다. 무채 역할은 속성이 앞서는 `--color-{bg|text|border}-{변형}-{상태}`, 강조·상태 역할은 역할이 앞서는 `--color-{accent|danger|…}-{subtle|border|solid|text}-{상태}`다.

```css
--color-bg-surface
--color-text-secondary
--color-border-strong
--color-accent-solid-hover
--color-danger-subtle
--color-accent-text
```

한 개념에 한 낱말만 쓴다. `--color-text-primary`를 본 사람이 `--color-text-disabled`를 보지 않고 짐작할 수 있어야 한다.

| 개념     | 고를 것  | 섞지 않을 것                                 |
| -------- | -------- | -------------------------------------------- |
| 글자색   | `text`   | `fg`, `foreground`, `content`, `ink`         |
| 배경     | `bg`     | `background`, 동의어로서의 `surface`, `fill` |
| 가장자리 | `border` | `stroke`, `outline`, `line`                  |
| 브랜드   | `accent` | `primary`, `brand`, `theme`를 뒤섞어 쓰기    |

`primary`는 한 가지 뜻에만 쓴다. 본문 글자의 `--color-text-primary` 옆에 브랜드의 `--color-primary`가 있는 것이 가장 흔한 이름 충돌이다. 브랜드는 `accent`로 하고 `primary`는 「그 묶음에서 가장 두드러진 것」으로 둔다.

나쁜 이름:

| 이름                         | 문제                                                 | 대신                                  |
| ---------------------------- | ---------------------------------------------------- | ------------------------------------- |
| `--color-blue-button`        | 의미 층에 생김새가 있다. 브랜드가 바뀌면 거짓이 된다 | `--color-accent-solid`                |
| `--color-sidebar-gray`       | 처음 쓴 자리 이름이다. 두 번째 쓰임에서 말이 안 된다 | `--color-bg-surface`                  |
| `--color-light-gray`         | 어두운 모드에서는 어두운 쪽이라 거짓이 된다          | 원시로서 `--neutral-200`              |
| `--color-text-2`             | 번호 의미는 뜻이 없다. `3`이 무엇일지 아무도 모른다  | `--color-text-secondary`              |
| `--color-gray-hover`         | 색조와 상태가 섞여 어느 층에도 속하지 않는다         | `--color-bg-surface-hover`            |
| 컴포넌트에서 쓴 `--blue-600` | 의미 층을 건너뛰어 테마 이음매가 없어진다            | 의미 토큰이 가리키게 하고 그것을 쓴다 |

Tailwind v4는 `@theme`에서 유틸리티를 만든다. 거기 선언한 이름이 API가 되므로 원시와 의미를 같은 블록에 선언한다. `--color-*` 이름 공간이 `bg-*`·`text-*`·`border-*`를 만든다.

```css
@theme {
  /* 원시 */
  --color-blue-50: #eff6ff;
  --color-blue-600: #2563eb;
  --color-blue-900: #1e3a8a;

  /* 의미: 템플릿이 쓸 것 */
  --color-accent-solid: var(--color-blue-600);
  --color-text-secondary: var(--color-neutral-700);
}
```

- 이렇게 하면 `bg-accent-solid`와 `text-text-secondary`가 `bg-blue-600`과 함께 생긴다. Tailwind가 모든 `--color-*` 이름 앞에 유틸리티 접두어를 붙이므로 `text-` 토큰은 겹쳐 보인다. 겹침을 받아들이거나 프로젝트가 이미 쓰는 관례를 따른다. 두 층이 다 닿으므로 규율은 제약이 아닌 관례다. 템플릿은 의미 유틸리티를 쓰고, 컴포넌트의 `bg-blue-600`이 걸러 낼 대상이다.
- 어두운 모드의 의미 토큰은 `@theme` 밖 `.dark` 블록에서 다시 가리킨다. `inline` 없이 두어야 유틸리티가 렌더 때 의미 변수를 읽는다.
- 불투명도 수정자(`bg-accent-solid/50`)는 두 층에 다 되지만 알파가 있는 색은 정적 배경에 대해 대비를 잴 수 없다(뒤에 놓인 것에 따라 렌더가 달라지므로). 글자가 놓이는 곳에는 불투명 토큰을 쓴다.

## 8. 색의 쓰임

토큰은 제 역할에만 쓴다. 지금 값이 맞아 보여도 빌리지 않는다. 구분선 토큰을 글자 색으로 쓰면 테두리가 옅어질 때 글자도 같이 옅어진다. 역할에 토큰이 없으면 토큰을 더한다.

```css
/* 나쁨: 구분선 토큰을 글자 색으로 빌림 */
.caption {
  color: var(--color-border);
}

/* 나쁨: 글자 토큰을 배경으로 빌림 */
.tag {
  background: var(--color-text-secondary);
}
```

한 색 한 뜻이다. 색조가 어긋난 근사치는 다른 색으로 읽히지 않고 조금 다른 음영으로 읽힌다. OKLCH 색조 `15°` 안은 같은 색으로 본다.

```css
/* 나쁨: 강조색이 「링크」이자 「장식 제목」 */
a {
  color: #3b82f6;
}
.section-title {
  color: #4f8ef7;
}

/* 좋음: 누를 수 있는 것이 강조색을 쓰고 제목은 무채 */
a {
  color: var(--color-accent-text);
}
.section-title {
  color: var(--color-text-primary);
}
```

반대 방향도 같다. 색의 뜻이 있어야 할 자리에 색이 없어도 틀리다. 강조색이 「누를 수 있음」이면 누를 수 있는데 무채색인 것도 오해를 부른다.

색만으로 뜻을 전달하지 않는다. 아이콘이나 글과 함께 쓴다. 요구 사항은 `ux-a11y`가 정한다.

화면당 채운 행동은 하나다. 채움 색이 주요 강조를 나타내면 주요 행동 하나가 쓰고 나머지는 무채로 둔다. 색은 글자가 아닌 배경에 둔다. 채운 버튼은 멀리서도 주요로 읽히고, 무채 버튼의 강조색 글자는 링크로 읽힌다. 이미 다른 방식으로 강조를 나타내는 위계는 유지한다. 구분되는 상태나 분류를 나타내는 여러 색 배경은 같은 급으로 경쟁하지 않으므로 괜찮다. 선택된 상태(활성 탭, 체크된 세그먼트)의 강조색 글리프·라벨은 강조가 아니라 상태다.

```html
<!-- 좋음: 채운 주요 행동 하나, 나머지는 무채 -->
<button class="bg-accent-solid text-text-on-accent">저장</button>
<button class="text-text-secondary">취소</button>

<!-- 나쁨: 전부 색칠해서 무엇도 주요가 아님 -->
<button class="bg-accent-solid text-text-on-accent">저장</button>
<button class="bg-accent-solid text-text-on-accent">복제</button>
<button class="bg-accent-solid text-text-on-accent">내보내기</button>
```

그라데이션: 보간 공간은 정확성 설정이 아니고 모양의 선택이다. 차이는 가운데에서 가장 잘 보인다.

```css
/* sRGB: 기본. 가운데가 어둡고 탁하다 */
background: linear-gradient(#3b82f6, #ec4899);

/* oklab: 전 구간 밝기가 고르다. 가장 좋은 기본 */
background: linear-gradient(in oklab, #3b82f6, #ec4899);

/* oklch: 색상환을 돌아가며 내내 선명하다 */
background: linear-gradient(in oklch, #3b82f6, #ec4899);
```

- `oklab`과 sRGB는 직교 공간이라 색 공간을 가로지르는 직선으로 보간한다. `oklch`는 극좌표라 색조 각도를 보간하므로 중간의 모든 색조를 지나 호를 그린다. 그래서 선명하게 유지되고 요청하지 않은 색조도 나올 수 있다. 파랑에서 분홍은 보라를 지난다.
- 회색 죽은 구간은 직교 공간의 문제다. 색상환 반대편 두 색조는 무채 축 양쪽에 있어 직선이 회색 근처를 지나 가운데가 생기를 잃는다. 극좌표 공간으로 바꾸거나 두 색 사이에 정지점 하나를 더하고 지금 공간을 유지한다.
- 극좌표 공간에서는 어느 쪽으로 도는지 정한다(`shorter hue`가 기본이고 대개 맞다, `longer hue`는 스펙트럼 대부분을 쓴다).

```css
background: linear-gradient(in oklch shorter hue, #3b82f6, #ec4899);
background: linear-gradient(in oklch longer hue, #3b82f6, #ec4899);
```

- 넓은 면은 계단(banding)이 보인다. 정지점 사이 대비가 작은 큰 히어로 그라데이션은 8비트 화면에서 계단이 생긴다. 대비를 키우거나 면을 줄이거나 옅은 노이즈를 덮는다.
- 글자는 그라데이션 위에 두지 않는다. 대비가 연속으로 달라 측정 하나가 전체를 말하지 못한다. 글자가 꼭 올라가면 가장 나쁜 곳을 재거나 뒤에 스크림을 둔다.

## 9. 밝은 모드·어두운 모드·고대비

어두운 모드가 있으면 모든 맞춤 색에 어두운 값이 필요하다. 어두운 묶음은 밝은 묶음을 뒤집은 것이 아니다. 뒤집기는 시작점이다.

의미 역할을 먼저 바꾸고 값을 조정한다.

```css
:root {
  --color-bg-page: var(--neutral-50);
  --color-text-primary: var(--neutral-950);
}

.dark {
  --color-bg-page: var(--neutral-950);
  --color-text-primary: var(--neutral-50);
}
```

바꾼 뒤 거의 항상 손으로 조정할 것:

- 선명도를 낮춘다. 흰 바탕에서 자신 있어 보이는 색이 거의 검정 바탕에서는 네온처럼 보인다. 어두운 모드의 강조는 한두 단계 덜 선명하게 한다.
- 어두운 끝에 간격이 더 필요하다. 옅은 배경으로는 구분되던 단계들이 어두운 면에서는 뭉친다.
- 대비는 뒤집어도 유지되지 않는다. APCA는 짝을 뒤집으면 다르게 매기므로 모든 짝을 두 모드에서 다시 잰다.

전환 방식은 하나만 쓴다.

- `prefers-color-scheme`만: 테마 토글이 없을 때 맞다. 저장하거나 수화할 것이 없다.
- `.dark` 클래스: 사용자가 시스템 설정을 덮어쓸 수 있으면 필요하다. 그때 미디어 쿼리는 초기값만 정한다.
- `light-dark()`: 두 값을 한 선언에 둔다. `color-scheme: light dark`가 필요하고 클래스 대신 그 속성을 읽으므로 클래스 토글은 `color-scheme`도 바꿔야 한다.

```css
:root {
  color-scheme: light dark;
  --color-bg: light-dark(#ffffff, #172554);
}
```

미디어 쿼리가 일부 토큰을 정하고 클래스가 다른 토큰을 정하면 사용자가 시스템 설정을 덮어쓰는 순간 화면이 반만 바뀐다.

고대비(`prefers-contrast: more`)는 모드마다 값을 따로 둔다. 사용자는 각 모드에서 구분이 눈에 띄게 강해지기를 기대한다.

```css
:root {
  --color-accent-solid: var(--blue-600);
}

@media (prefers-contrast: more) {
  :root {
    --color-accent-solid: var(--blue-900);
  }
}

@media (prefers-color-scheme: dark) {
  :root {
    --color-accent-solid: var(--blue-400);
  }
}

@media (prefers-color-scheme: dark) and (prefers-contrast: more) {
  :root {
    --color-accent-solid: var(--blue-200);
  }
}
```

한 블록이 두 모드에 공통이면 어두운 바탕에서도 색이 어두워져 대비가 오히려 줄어든다. 고대비 변형은 기본값보다 바탕과의 OKLCH `L` 간격을 `0.15` 이상 벌리고 다시 잰다. 본문 글자는 Lc 90을 목표로 한다. 간격을 벌리고 다시 재지 않으면 고친 것이 아니다.

## 10. 대비는 실제 짝으로 잰다

전경(글자·아이콘·UI 요소)을 그것이 실제로 놓인 배경에 대고 잰다. 보통 색을 칠하는 가장 가까운 상위 요소다. 카드 위 요소를 페이지 배경과 재면 답이 틀리다. 배경을 먼저 찾는다.

- 글자 바로 아래 그려지는 배경을 쓴다. 투명도와 이미지도 포함한다.
- 실패하면 짝, 잰 값, 못 넘은 기준을 보고하고 색은 그대로 둔다. 색은 디자인 결정이다. 요청받으면 밝기를 바꾸고 다시 잰다.
- 어느 요구를 적용할지는 `ux-a11y`가 정하고, 이 절의 수치는 잰 짝을 대어 보고하는 기준이다. 프로젝트나 `ux-a11y`가 기준을 정하지 않았으면 WCAG 2 결과를 보고하고 APCA 값을 더한다.

WCAG 2(공식 적합 주장의 기준):

| 내용                                      | AA    | AAA       |
| ----------------------------------------- | ----- | --------- |
| 글자                                      | 4.5:1 | 7:1       |
| 큰 글자(24px 이상 또는 굵은 18.67px 이상) | 3:1   | 4.5:1     |
| UI 컴포넌트와 그래픽 객체                 | 3:1   | 해당 없음 |

비활성 컨트롤과 로고는 예외다.

APCA(Lc는 지각 대비 측정값이다. 아래는 글자 크기·굵기 조견표를 단순화한 것이다):

| 내용                                        | 최소              |
| ------------------------------------------- | ----------------- |
| 본문(칸·덩어리 글)                          | Lc 75, 권장 Lc 90 |
| 본문이 아닌 글(라벨·헤드라인)               | Lc 60             |
| 큰 글자(보통 36px 이상 또는 굵은 24px 이상) | Lc 45             |
| 가는 선 아이콘                              | Lc 45             |
| 채운 아이콘·UI 컴포넌트                     | Lc 30             |
| 구분선처럼 식별만 되면 되는 비글자          | Lc 15             |

비활성 글자와 플레이스홀더는 요구가 없다. 읽히게 Lc 30을 목표로 한다. Lc는 부호가 있다. 양수는 밝은 바탕의 어두운 글자, 음수는 어두운 바탕의 밝은 글자이므로 절댓값을 기준과 비교한다.

고치기(요청이 있을 때만):

- 밝기를 먼저 바꾼다. 대비가 반응하는 채널이 밝기다. 색조와 채도는 측정값을 훨씬 덜 움직인다. 색조·채도를 두고 전경을 바탕에서 지각 밝기로 멀리 둔 뒤 다시 잰다. 색조를 두면 대비 수정이 팔레트 변경이 되지 않는다.
- 중간 밝기 배경은 얻을 수 있는 한계를 정한다. OKLCH `L` `0.75` 근처 배경에서는 순검정 글자도 Lc 60 정도에 그친다. 본문은 한쪽 끝에 가까운 배경이 필요하므로 바꿀 것은 중간 밝기의 배경이다.
- 밝기를 밀면 색이 색역을 벗어날 수 있다. 렌더 가능하도록 채도를 낮춘다(6절).
- 값을 바꾸면 반드시 다시 잰다. 고쳐졌다고 가정하지 않는다.

```css
/* 실패: 글자가 배경과 밝기가 가깝다 (Lc ≈ 50) */
color: #7d93b0;
background: #eef2f7;

/* 수정: 더 어두운 글자, 같은 색조 (Lc ≈ 88) */
color: #2b3a4f;
background: #eef2f7;
```

글자 극성은 배경에서 고른다. 프로젝트가 요구하는 대비 지표로 검정과 흰색을 비교한다. APCA와 WCAG 2는 같은 배경에서 다른 글자 색을 선호할 수 있다. 점수가 높다고 통과는 아니다. WCAG 2의 무채 교차점은 OKLCH 밝기 56% 근처다. `oklch(65% 0 0)`에서 검정은 약 `6.49:1`, 흰색은 `3.23:1`이라 일반 글자는 검정만 AA를 통과한다. 색이 있는 배경이나 다른 전경은 교차점을 적용하지 말고 실제 짝을 잰다.

확인할 것:

- 모든 짝을 모든 모드에서 잰다. APCA는 뒤집은 짝을 다르게 매기므로 밝은 모드에서 통과한 짝이 어두운 모드에서 실패할 수 있다.
- 반투명 면: `backdrop-filter` 헤더나 오버레이 위의 색은 뒤로 스크롤되는 것에 따라 바뀐다. 올 수 있는 가장 밝은·어두운 내용에 대고 재거나, 이동이 짝을 깨뜨리지 못할 만큼 불투명하게 한다.
- 계산된 색: `color-mix()`·상대 색 문법·불투명도 수정자는 렌더 때 풀리므로 선언이 아니라 렌더 결과를 잰다.
- 이미지 위 글자: 배경색이 하나가 아니다. 가장 나쁜 영역을 재거나 스크림으로 하나를 보장한다.

## 11. 기존 팔레트 정리

체계를 다시 짜기 전에 목록부터 만든다. 대부분의 코드베이스는 디자인 결정보다 몇 배 많은 색이 들어 있다.

1. 모든 색 값을 모은다. hex·`rgb(`·`hsl(`·`oklch(`와 프로젝트의 유틸리티 접두어를 검색한다. SVG `fill`·`stroke`, 차트 설정, 메일 템플릿도 포함한다.
2. 색조별로 지각 밝기를 정렬한다. 거의 같은 이웃으로 중복이 바로 보인다.
3. 근사 중복을 합친다. OKLab ΔE `0.02` 안의 두 색은 어긋난 한 색이다. 가장 많이 쓰인 것을 두고 나머지는 은퇴시킨다. 평균내지 않는다.
4. 남은 색에 2절의 역할을 붙인다. 어떤 역할에도 안 맞는 색은 빠진 토큰이거나 실수다. 어느 쪽인지 정해서 finding에 적는다.
5. 남은 묶음 수를 집계한다. 2절이 든 묶음보다 많으면 제품이 색을 더 필요로 하는 것이 아니고 팔레트가 구조를 넘어선 것이다.

바꾸기 전에 목록을 보고한다. 팔레트를 통합하면 요청하지 않은 화면의 렌더가 바뀌므로 사용자가 받아들이기 전에는 제안으로만 둔다.

## 12. 한글 화면 기준

이 절은 이 하네스가 한국어 화면에 맞춰 더했다. 원본에 없다.

원본은 금융 색의 지역 차이로 중국 화면(상승 빨강·하락 초록, 영어권과 반대)을 든다.

| 항목                      | 기준                                                                                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 한글 금융 색              | 금융 색은 지역마다 다르다. 한국 증권 화면은 상승 빨강 · 하락 파랑이고, 미국은 상승 초록 · 하락 빨강이다                                                          |
| 한글 오르내림 토큰        | 오르내림은 지역별 의미 토큰 `--color-gain` · `--color-loss`로 둔다. 한국에서는 상승이 빨강이라 위험 색과 겹치므로 `--color-danger`를 오르내림에 빌려 쓰지 않는다 |
| 한글 색만으로 말하지 않기 | 오르내림에는 ▲▼와 부호(`+`·`-`)를 함께 써서 색만으로 말하지 않는다. 색각 이상 사용자와 지역 관례가 다른 사용자도 같은 뜻을 읽는다                                |

```css
:root[lang="ko"] {
  --color-gain: var(--red-600);
  --color-loss: var(--blue-600);
}

:root[lang="en-US"] {
  --color-gain: var(--green-600);
  --color-loss: var(--red-600);
}
```

## 13. 끝내기 전 찾을 것

| 찾을 것                                                                           | 고칠 것                                                                             |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 토큰이 있는데 컴포넌트 파일에 쓴 hex·`rgb(`·`oklch(` 리터럴                       | 역할 토큰을 재사용하거나 더한다(프로젝트 표기법으로)                                |
| 나머지가 hex인 코드베이스에 하나만 있는 `oklch(` 값                               | 이전이 범위에 없으면 정해진 표기법으로 쓴다                                         |
| 컴포넌트 파일의 `var(--blue-600)`·`bg-blue-600`                                   | 의미 토큰이 원시를 가리키게 하고 그것을 쓴다                                        |
| 색조나 컴포넌트가 들어간 의미 이름(`--color-blue-button`, `--color-sidebar-gray`) | 역할 이름으로 바꾼다: `--color-accent-solid`, `--color-bg-surface`                  |
| `--color-primary`와 `--color-text-primary`가 둘 다 정의됨                         | 브랜드 토큰을 `accent`로 바꾼다                                                     |
| `color:` 안의 `border`·`separator` 토큰, `background:` 안의 `text` 토큰           | 빠진 역할의 토큰을 더한다                                                           |
| 밝기만 다른 `hsl(` 묶음 값                                                        | 프로젝트 표기법으로 지각 색조가 일정하게 다시 만든다                                |
| OKLCH `L` 간격이 가운데 단계만큼 벌어진 `50`\~`200`                               | 밝은 끝을 단계당 약 `0.04`\~`0.05`로 조인다                                         |
| 모든 색조 묶음에 복사한 chroma·채도 숫자 하나                                     | 각 색조가 닿는 최대 선명도의 같은 비율을 쓴다                                       |
| 강조 색조에서 `15°` 안에 있는 상태 색조                                           | 최소 `15°` 떨어뜨리거나 파괴 동작에 다른 처리를 준다                                |
| 밝은 묶음을 단계 역순으로 뒤집기만 한 어두운 토큰                                 | 강조 chroma를 낮추고 어두운 끝을 넓히고 모든 짝을 다시 잰다                         |
| `prefers-color-scheme`과 `.dark` 클래스 아래 함께 놓인 색 토큰                    | 전환 방식을 하나 고르고 전체에 쓴다                                                 |
| 색조는 바꾸고 밝기는 두는 대비 수정                                               | 대비가 반응하는 채널인 밝기를 바꾼다                                                |
| 두 모드를 한 블록에서 덮어쓰는 `prefers-contrast: more`                           | 모드마다 고대비 값을 따로 준다                                                      |
| 알파가 있는 색 위의 글자(`/50`, `rgba(`, `transparent`와 `color-mix(`)            | 렌더 결과를 재거나 불투명 토큰을 쓴다                                               |
| Tailwind `500` 채움 위의 `text-white`                                             | 잰다. 흰 글자는 대부분의 `500` 색조에서 4.5:1에 못 미치므로 채움을 `600`으로 바꾼다 |
| sRGB 값을 먼저 선언하지 않은, sRGB 밖 chroma의 `oklch()`                          | sRGB 값을 먼저 선언하고 선명한 값은 `@media (color-gamut: p3)` 안에 둔다            |

## 14. 점검할 때 심각도와 확인

| 등급 | 기준                                               |
| ---- | -------------------------------------------------- |
| P1   | 내용을 읽을 수 없거나 오해하게 하는 의미 색을 쓴다 |
| P2   | 눈에 띄는 테마·토큰·색역 실패                      |
| P3   | 한 곳에 그친 다듬기                                |

화면이 어떤 곳이든 바로 P1인 것(원본이 등급을 올리는 조건으로 둔 항목)이 셋이다.

- 본문이나 컨트롤 글자의 실제 짝이 요구 대비를 못 넘는다.
- 상태나 뜻을 색만으로 전달한다.
- 의미 색을 그 뜻과 반대로 쓴다.

브라우저 없이 확인할 것: 토큰 값, 선언된 모든 색의 색역, 두 모드 블록의 존재, 선언된 토큰 짝으로 계산한 대비.

브라우저에서 확인할 것: 글자 뒤에 실제로 그려지는 배경(투명도와 그 밑의 이미지 포함)을 밝은 모드와 어두운 모드에서 잰다.

못 한 확인은 「확인 못 함」으로 적는다. 보지 않은 범위는 통과로 적지 않는다.
