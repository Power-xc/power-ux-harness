# UX Research

알고 싶은 것을 결정 하나로 좁히고, 그 결정에 맞는 방법으로 사용자에게서 증거를 모은다. 리서치는 비교표가 아니라 결정으로 끝난다.

## Trigger

- `@ux research <질문>`: 리서치 계획 수립
- `@ux interview <주제>`: 인터뷰 가이드와 질문 작성
- `@ux usability-test <화면|흐름>`: 사용성 테스트 과제·진행 대본·관찰 양식
- 인터뷰 결과·녹취·설문 응답을 정리해 인사이트와 다음 결정을 뽑는 요청

## Input

- `decision`: 이 리서치로 내릴 결정(예: 해지 흐름을 고칠지, 어디부터)
- `question`: 알고 싶은 것
- `audience`: 대상 사용자와 제외할 사용자
- `constraints`: 기간, 인원, 원격·대면, 보상
- `data`: 이미 있는 지표·문의·녹취·설문(정리 모드)

decision이 없으면 question에서 가장 그럴듯한 결정을 하나 제안하고 가정으로 표시한다.

## Evidence Levels

- `observed`: 참가자가 과제에서 실제로 한 행동
- `reported`: 참가자가 말한 생각·경험·의견
- `hypothesis`: 리서치 전의 가정 또는 해석

말한 것과 한 것을 구분해 적는다. 참가자의 의견을 행동 증거처럼 쓰지 않는다.

## Process

1. decision과 question을 각각 한 문장으로 고정한다. 결정과 이어지지 않는 질문은 범위에서 뺀다.
2. 질문을 세 축에 놓는다 — 말한 것과 한 일, 왜와 얼마나, 실제 맥락과 짜인 과제. [`references/methods.md`](./references/methods.md)에서 축에 맞는 방법을 고르고 고르지 않은 방법과 이유를 한 줄씩 적는다.
3. 인원을 정한다. 반복 사용성 테스트는 라운드당 5명, 사용자 집단이 둘이면 집단당 3~4명, 카드 소팅은 15명, 수치로 비교할 정량 연구는 40명을 기준으로 하고 기준과 다르면 이유를 적는다.
4. 모집 조건과 스크리너 질문을 쓴다. 스크리너는 원하는 답이 드러나지 않게 쓰고, 제외 조건(관계자·최근 참여자)을 넣는다.
5. 인터뷰는 [`references/interview-guide.md`](./references/interview-guide.md)의 규칙으로 쓴다. 미래 의향 대신 최근의 실제 경험을 묻고, 유도 질문·예/아니요 질문·한 번에 두 개를 묻는 질문을 고친다.
6. 사용성 테스트 과제는 현실적인 목표와 맥락을 주고, 화면의 라벨이나 누를 위치를 알려 주지 않는다. 과제마다 성공 기준과 관찰할 행동을 미리 적는다.
7. 진행 대본에 동의·녹화 안내, 생각 말하기 안내, 개입 규칙(계속 말하게 하는 말만 하고 힌트를 주지 않는다)을 넣는다.
8. 정리 모드에서는 관찰 메모를 한 줄 한 사실로 쪼개고, 참가자 ID를 붙여 묶는다. 묶음마다 몇 명에게서 나왔는지 세고, 한 명만의 의견을 패턴으로 쓰지 않는다.
9. 인사이트는 「관찰 → 해석 → 결정에 주는 의미」 순서로 쓰고, 해볼 것 하나와 하지 말 것 하나로 끝낸다. 버린 가설과 버린 이유도 적는다.

## Output

- 계획 모드: 결정·질문, 방법과 고르지 않은 방법, 인원과 근거, 모집 조건·스크리너, 인터뷰 가이드 또는 과제 목록, 진행 대본, 일정, 윤리·개인정보 처리
- 정리 모드: 참가자 표(ID·조건, 실명 없음), 묶음별 관찰과 인원 수, 인사이트(증거 수준 표시), 해볼 것·하지 말 것, 버린 가설, 다음 리서치 질문
- 판정: 계획은 아래 게이트를 모두 지나면 `READY`, 아니면 `NOT_READY`와 빠진 항목

## Hard Gates

| ID  | FAIL 조건                                                           |
| --- | ------------------------------------------------------------------- |
| G1  | 리서치로 내릴 결정이 없거나 질문이 결정과 이어지지 않음             |
| G2  | 인터뷰·과제에 유도 질문, 예/아니요 질문, 화면 라벨 노출이 남아 있음 |
| G3  | `reported`(말한 것)를 `observed`(한 일) 증거처럼 씀                 |
| G4  | 한 명의 의견을 여러 사용자의 패턴으로 일반화                        |
| G5  | 동의·녹화·개인정보 처리 안내 없이 진행 계획을 확정                  |
| G6  | 정량 비교를 소수 정성 결과의 비율로 주장(예: 5명 중 3명 = 60%)      |

## Skill Chaining

- 결과로 흐름을 다시 그리기: `ux-flow`
- 관찰한 문제를 화면에서 우선순위로 정리: `ux-review`
- 정량으로 확인할 지표 설계: `ux-metrics`
- 인터뷰 질문·안내문의 문장 다듬기: `ux-writing`

## Constraints

- 참가자 실명·연락처·얼굴을 산출물에 넣지 않는다. 참가자는 P1, P2처럼 부른다.
- 미성년자·취약 집단 리서치는 보호자 동의와 별도 승인 절차를 계획에 넣는다.
- 리서치 없이 만든 페르소나를 사실처럼 쓰지 않는다. 근거가 없으면 가정 페르소나라고 적는다.
- AI가 만든 가상 응답을 실제 참가자 데이터로 섞지 않는다.
- 이미 답이 정해진 결정을 정당화하려고 리서치를 설계하지 않는다.
