# UX Accessibility

장애가 있는 사용자도 같은 과제를 끝낼 수 있는지 기준 번호로 판정한다. 자동 검사는 출발점이고, 판정은 직접 확인한 것으로 한다.

## Trigger

- `@ux a11y <화면|URL|흐름>`: 접근성 감사
- 「접근성 점검해 줘」, 「WCAG 맞는지」, 「웹 접근성 인증 준비」, 「스크린 리더로 쓸 수 있나」, 「명도 대비」, 「터치 영역 크기」

## Input

- `target`: URL, 로컬 실행 경로, 화면 캡처, Figma 프레임, 코드
- `platform`: 웹 · iOS · Android
- `standard`: 기본 WCAG 2.2 AA. 국내 공공·인증 범위면 KWCAG 2.2, 모바일 앱이면 KS X 3253:2025를 함께 대조
- `scope`: 과제와 화면 범위

## Evidence Levels

- `automated`: 자동 검사 도구의 결과(도구 이름·버전 기록)
- `manual`: 키보드·화면 낭독기·확대로 직접 확인
- `code-inferred`: 마크업·코드로 확인했지만 실행하지 못함
- `NOT_CHECKED`: 범위 안이지만 확인하지 못함

자동 검사는 기준의 일부만 잡는다. 자동 결과만으로 적합을 판정하지 않는다. 다른 스킬의 보고서와 합칠 때 `automated`·`manual`은 `observed`로 묶는다.

## Process

1. 기준과 수준을 고정한다. [`references/wcag22-checklist.md`](./references/wcag22-checklist.md)가 기본 목록이고, 국내 범위면 [`references/kwcag-mapping.md`](./references/kwcag-mapping.md)로 검사 항목 번호를 함께 적는다.
2. 실행할 수 있으면 자동 검사(axe-core·Lighthouse 등)를 돌리고 도구 이름·버전·위반 규칙을 기록한다.
3. 키보드만으로 과제를 끝까지 해 본다 — 순서, 보이는 포커스, 고정 막대·배너·토스트에 완전히 가려지는 포커스, 키보드 함정, 건너뛰기 링크, 대화상자의 포커스 이동과 복귀.
4. 화면 낭독기로(없으면 코드로) 이름·역할·상태, 제목·랜드마크 구조, 이미지 대체 텍스트, 폼 라벨, 상태 메시지 알림, 오류 알림을 확인한다.
5. 시각 항목을 잰다 — 글자 대비 4.5:1(큰 글자 3:1), 아이콘·테두리 등 비텍스트 대비 3:1, 색만으로 전하는 정보, 320px 폭 재배치, 200% 확대, 글자 간격, 화면 방향 고정. 그림·그라데이션·반투명 면 위의 글자는 DOM 계산값이 아니라 렌더된 화면의 픽셀로 잰다 — 글자 뒤에서 글자색과 가장 가까운 배경 픽셀을 골라 계산하고 측정 방법을 적는다.
6. 포인터·터치를 확인한다 — 대상 크기 최소 24×24 CSS px(또는 24px 원이 겹치지 않는 간격), 끌기 동작의 한 번 누르기 대안, 복잡한 제스처의 대안, 누르는 순간이 아닌 떼는 순간 실행, 보이는 라벨과 접근 이름의 일치, 기기 흔들기 같은 동작의 대안. 앱은 플랫폼 권장(iOS 44×44pt, Android 48×48dp)과 함께 적는다.
7. 시간과 움직임 — 시간 제한(스스로 사라지는 알림 포함)의 끄기·늘리기, 자동 재생·움직임의 일시 정지, 번쩍임, 움직임 줄이기 설정. 5초 넘게 스스로 넘어가는 캐러셀·배너는 보이는 정지 버튼이 있는지, 포커스나 포인터가 올라가면 멈추는지 본다. 「다음」을 눌러야만 멈추는 방식은 멈출 수 있다는 사실이 드러나지 않아 2.2.2 위험으로 적는다.
8. 폼과 인증 — 같은 과정에서 다시 입력하게 하는지, 기억·옮겨 적기만 요구하는 인증인지, 오류 수정 제안, 도움말 위치의 일관성.
9. finding마다 기준 번호·이름·수준, 국내 범위면 KWCAG 검사 항목 번호, 위치, 증거 수준, 영향받는 사용자(화면 낭독기·저시력·운동·인지), 수정안(가능하면 코드 수준), 우선순위를 적는다. 특정 사용자 집단이 과제를 끝낼 수 없으면 P1이다.
10. 확인한 범위만 판정하고, 확인하지 못한 기준을 `NOT_CHECKED`로 나열한다.

## Output

- 판정: `PASS | FAIL | BLOCKED` — 범위 안에서 AA 위반이 하나라도 있으면 FAIL
- 기준·수준·플랫폼·범위·사용한 도구와 보조기기
- finding 표: `criterion`, `kwcag`(해당 시), `evidence`, `location`, `impact`, `fix`, `priority`
- 요약: 자동으로 찾은 것 · 직접 확인한 것 · 확인하지 못한 것

## Hard Gates

| ID  | FAIL 조건                                 |
| --- | ----------------------------------------- |
| G1  | 자동 검사 결과만으로 PASS 또는 적합 판정  |
| G2  | finding에 기준 번호가 없음                |
| G3  | 열어 볼 수 있는데 키보드 확인을 하지 않음 |
| G4  | WCAG 3 적합을 주장함(아직 초안이다)       |
| G5  | 실제 색 값 없이 대비 수치를 적음          |
| G6  | 국내 범위인데 KWCAG 검사 항목 번호가 없음 |

## Skill Chaining

- 접근성 밖의 사용성 문제: `ux-review`
- 대체 텍스트·링크 이름·오류 문구: `ux-writing`
- 접근성 메모를 화면 설계서에 반영: `ux-spec`
- AI 응답 화면의 상태 알림·중지 버튼: `ux-ai`

## Constraints

- 이 감사는 법정 인증이 아니다. 웹 접근성 인증은 지정 기관이 한다고 안내한다.
- 접근성 오버레이 위젯을 해결책으로 권하지 않는다.
- 포커스 표시를 없애는 수정을 권하지 않는다.
- 보조기기 사용자를 흉내 낸 결과를 실제 사용자 테스트처럼 쓰지 않는다.
- 운영 환경을 열 때는 쓰기·분석 요청(POST·비콘)을 막고 본다. 관찰이 운영 데이터를 바꾸지 않게 한다.
