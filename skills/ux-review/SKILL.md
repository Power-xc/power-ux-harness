# UX Review

사용자가 목표를 완수하는 실제 경로를 관찰하고, 근거 있는 최소 개선안을 우선순위로 정리한다.

## Trigger

- `@ux review <화면|흐름>`: 특정 화면 또는 연속 흐름 검토
- `@ux funnel <구간>`: 이탈 구간의 관찰 결과와 원인 가설 정리
- 사용성·온보딩·CTA·복구·권한 요청·결정 마찰 리뷰
- 토스트·스낵바·모달, 스피너·스켈레톤, 스위치·체크박스처럼 패턴 선택이 맞는지 묻는 요청
- 요금제 비교표·추천 강조·월·연 전환처럼 고르는 화면의 구성을 묻는 요청

## Input

- `target`: URL, 로컬 경로, 스크린샷, 프로토타입, 화면 설계서
- `goal`: 사용자가 완료해야 할 일
- `user`: 주요 사용자와 사용 맥락(기기·상황·숙련도)
- `evidence`: 지표, 피드백, 녹화, 문의 기록

goal과 user가 요청이나 제품에서 분명하면 다시 묻지 않는다. 추론했으면 산출물에 가정으로 적는다.

## Evidence Levels

- `observed`: 화면·프로토타입·녹화에서 직접 확인
- `code-inferred`: 코드와 상태 분기로 확인했지만 렌더링하지 못함
- `hypothesis`: 사용자 행동이나 원인을 추정

수준을 섞지 않는다. 보지 못한 동작을 `observed`로 쓰지 않는다.

## Process

1. 사용자, 진입점, 완료 조건을 한 문장으로 고정한다.
2. 열 수 있으면 실제 화면이나 프로토타입을 열고 핵심 과제를 처음부터 끝까지 수행한다. 이 첫 번째 통과에서는 흐름을 익히기만 한다. 이때 여는 빌드가 데모·목 데이터·기능 플래그 때문에 운영과 다르게 그려지는지(데모에서만 그리는 분기, 키가 없을 때의 대체 화면)도 확인한다 — 다르면 finding마다 관찰한 빌드를 적고, 데모에서 볼 수 없는 운영 분기는 코드 분기 표(조건·플래그 | 데모 | 운영 | 화면 차이 | 코드 위치)로 적어 `code-inferred`로 둔다.
3. 두 번째 통과에서 진입·이해·결정·행동·피드백·복구 단계별로 멈춤과 왕복을 기록한다. 데스크톱·모바일 뷰포트와 키보드 경로를 확인하고 캡처나 재현 가능한 위치를 남긴다. 전체 페이지 캡처는 하단 고정 막대를 문서 중간에 겹쳐 찍고 덮개(시트·대화상자)를 어긋나게 찍으므로, 고정 요소와 덮개는 화면 크기 캡처로 남기고 개발 서버가 띄우는 표식·오버레이는 캡처 전에 숨긴다.
4. 각 문제에 [`references/heuristics.md`](./references/heuristics.md)의 휴리스틱 하나를 주 근거로 붙인다. Laws of UX는 이유를 설명할 때만 쓰고 그 자체를 문제로 적지 않는다.
5. 빈 상태·콘텐츠가 거의 없는 초기 상태(콜드 스타트 — 오래된 글 한두 개만 보이는 피드)·로딩·오류·성공·권한·취소/뒤로·끝(더 없음·마지막 단계) 상태를 확인한다. 운영에서 오류·복구 상태를 안전하게 띄울 수 없으면 로컬·데모 빌드에서 읽기 요청을 실패시켜(네트워크 차단·요청 가로채기) 보고, 그것도 안 되면 코드의 분기를 읽어 `code-inferred`로 적는다. 적용되지 않으면 `N/A`와 이유를, 적용되는데 관찰도 코드 확인도 못 했으면(쓰기가 막힌 운영 관찰, 키 없는 데모, 코드 없음) `NOT_CHECKED`와 막힌 이유를 적고 판정에 「부분」을 붙인다.
6. 알림·입력·로딩·내비게이션·제스처·모션 요소를 패턴 이름으로 적고 [`references/pattern-fit.md`](./references/pattern-fit.md)와 대조한다. 알림은 방해 수준이 정보의 무게와 되돌릴 수 있는지에 맞는지 본다. 요금제·가격표는 같은 문서의 요금제 기준으로 비교 항목·추천 근거·청구 금액을 본다.
7. 폼·가입·결제가 범위에 있으면 [`references/forms-checkout.md`](./references/forms-checkout.md)의 질문 원칙·오류 계약·검증 시점·결제 점검을 적용한다.
8. 결제·구독·동의·해지가 범위에 있으면 기만 패턴을 `ux-dark-patterns`로 점검한다. 확인되면 P1이다.
9. 심각도 0\~4를 매기고 P1\~P3으로 옮긴다(4 → P1, 3 → P2, 1\~2 → P3, 0은 finding이 아니다). 빈도·영향·지속성을 함께 본다. 완료 화면과 오류 복구 화면의 문제는 기억에 오래 남으므로 같은 심각도 안에서 앞에 둔다. 핵심 과제를 끝내지 못하게 막으면 심각도 4다. 특정 조건(기기·권한·데이터 상태·세그먼트)에서만 막으면 P2로 두고 판정에 「조건부」와 그 조건을 붙인다.
10. 수정안에는 바꿀 패턴 이름, 해당 상태, 문구 초안을 적는다. 현재 구조에서 가능한 최소 수정과 관찰 가능한 acceptance criteria를 함께 쓴다.
11. 수정이 반영되면 같은 과제와 뷰포트로 다시 확인한다.

대상을 열 수 없으면 정적 휴리스틱 리뷰로 범위를 낮추고 런타임 항목은 `BLOCKED`로 보고한다. 지표가 없으면 이탈 원인을 hypothesis로 적는다.

## Output

- 판정: `PASS | FAIL | BLOCKED` — P1이 하나라도 있으면 FAIL. PASS에는 해당하면 「부분: 확인 못 한 상태와 이유」·「조건부: 완주를 막는 조건과 finding」을 붙인다
- 범위, 사용자 목표, 사용한 화면과 뷰포트, 가정
- finding 표: `priority`, `severity`(0~4), `heuristic`, `evidence_level`, `build`(관찰한 빌드 — 운영·데모), `location`, `steps`, `issue`(현재 패턴 이름 포함), `impact`, `fix`(패턴·상태·문구), `acceptance_criteria`
- 먼저 고칠 1~3건: 문제, 검토한 선택지, 고른 이유, 기대 지표 순으로 쓴다. 지표 근거가 없으면 hypothesis로 표시한다.
- `N/A`·`NOT_CHECKED` 상태와 남은 가설

## Hard Gates

| ID  | FAIL 조건                                                                                                      |
| --- | -------------------------------------------------------------------------------------------------------------- |
| G1  | 대상을 열 수 있는데 직접 관찰하지 않음                                                                         |
| G2  | 위치나 재현 단계 없이 개선안을 제안                                                                            |
| G3  | hypothesis를 관찰된 사용자 행동처럼 표현                                                                       |
| G4  | 적용되는 오류·복구 상태를 관찰도 코드 확인(`code-inferred`)도 하지 않고, 막힌 이유와 「부분」 표시도 없이 PASS |
| G5  | 우선순위·acceptance criteria 없이 finding을 나열                                                               |
| G6  | 수정안이 패턴·상태·문구 없이 방향만 제시                                                                       |
| G7  | 결제·구독·동의·해지 흐름을 기만 패턴 점검 없이 PASS하거나, 전환을 높이려고 기만 패턴을 권고                    |
| G8  | 데모와 운영이 다르게 그려지는 화면을 데모 관찰만으로 운영 판정                                                 |

## Skill Chaining

- 접근성 기준(WCAG 2.2·KWCAG) 감사: `ux-a11y`
- 기만 패턴과 규제 유형 점검: `ux-dark-patterns`
- 오류·버튼·빈 상태·알림 문구 작성: `ux-writing`
- 패턴을 들일 근거로 다른 서비스 사례가 필요할 때: `ux-benchmark`
- 수정안을 화면 설계서로 옮기기: `ux-spec`
- 원인 가설을 사용자로 검증: `ux-research`
- 수정 효과를 재는 지표: `ux-metrics`
- AI 응답 화면의 신뢰·통제 점검: `ux-ai`

## Constraints

- 취향을 사용성 문제로 포장하지 않는다.
- 전면 재설계보다 검증 가능한 최소 수정을 우선한다.
- 경쟁 제품에 있다는 이유만으로 패턴을 권하지 않는다. 사용자가 많은 선택지를 비교하는지, 골라 둔 소수를 확인하는지로 판단한다.
- 이미 관습이 된 아이콘과 제스처는 바꾸지 않는다.
- 개인정보가 담긴 캡처와 로그를 노출하지 않는다.
- 관찰 범위 밖의 화면을 제품 전체 판정으로 일반화하지 않는다.
- 수정 후 다시 확인하지 못했으면 완료가 아니라 남은 위험으로 보고한다.
- 운영 환경을 열 때는 쓰기·분석 요청(POST·비콘)을 막고 본다. 관찰이 운영 데이터를 바꾸지 않게 한다.
