# 휴리스틱 평가 기준

출처: NN/g Jakob Nielsen「10 Usability Heuristics for User Interface Design」(1994, 2024 검토)·「Severity Ratings for Usability Problems」(1994), Kate Moran·Kelley Gordon「How to Conduct a Heuristic Evaluation」(2023), Jon Yablonski『Laws of UX』(2판, 2024)와 lawsofux.com. 원문 문장을 옮기지 않고 리뷰 절차에 맞게 요약했다.

## 1. 10 휴리스틱

finding마다 아래 중 하나를 주 근거로 붙인다. 둘 이상에 걸치면 사용자 영향이 가장 큰 쪽을 고른다.

| #   | 휴리스틱                                                                             | 확인 질문                                                 | 흔한 finding                                                     |
| --- | ------------------------------------------------------------------------------------ | --------------------------------------------------------- | ---------------------------------------------------------------- |
| 1   | 시스템 상태의 가시성 (Visibility of system status)                                   | 누른 뒤 무슨 일이 일어났는지 바로 보이는가                | 저장 후 반응 없음 · 진행 표시 없는 긴 대기                       |
| 2   | 현실 세계와의 일치 (Match between the system and the real world)                     | 사용자의 말과 순서로 되어 있는가                          | 내부 용어·코드값 노출 · 업무 순서와 다른 화면 순서               |
| 3   | 사용자 통제와 자유 (User control and freedom)                                        | 실수에서 빠져나갈 출구가 있는가                           | 되돌리기 없는 삭제 · 닫을 수 없는 시트 · 뒤로 가면 입력이 사라짐 |
| 4   | 일관성과 표준 (Consistency and standards)                                            | 같은 것은 같은 이름·위치·모양인가, 플랫폼 관례를 따르는가 | 화면마다 다른 버튼 이름 · 관례와 다른 아이콘 뜻                  |
| 5   | 오류 예방 (Error prevention)                                                         | 오류가 나기 전에 막는가                                   | 형식 자유 입력 · 되돌릴 수 없는 일에 확인 없음                   |
| 6   | 기억보다 인식 (Recognition rather than recall)                                       | 앞 화면의 정보를 외워야 하는가                            | 이전 단계 선택을 다시 입력 · 숨은 옵션                           |
| 7   | 사용의 유연성과 효율성 (Flexibility and efficiency of use)                           | 자주 쓰는 사람의 지름길이 있는가                          | 반복 작업에 일괄 처리 없음                                       |
| 8   | 미학적이고 최소한의 디자인 (Aesthetic and minimalist design)                         | 결정에 필요 없는 정보가 경쟁하는가                        | 주요 행동을 가리는 배너·장식                                     |
| 9   | 오류의 인식·진단·복구 지원 (Help users recognize, diagnose, and recover from errors) | 오류가 쉬운 말로 원인과 해결을 말하는가                   | 「오류가 발생했습니다」만 표시 · 입력값 삭제                     |
| 10  | 도움말과 문서 (Help and documentation)                                               | 필요한 순간 그 자리에서 도움을 찾는가                     | 고객센터 안내만 있음                                             |

## 2. 심각도와 우선순위

| 심각도 | 뜻                                                                                  | 우선순위         |
| ------ | ----------------------------------------------------------------------------------- | ---------------- |
| 4      | 재앙 — 출시 전에 반드시 고친다. 목표 완수 불가, 데이터나 돈의 손실, 기만, 접근 차단 | P1               |
| 3      | 큰 문제 — 먼저 고친다. 흐름 멈춤, 왕복, 어려운 복구                                 | P2               |
| 2      | 작은 문제 — 낮은 우선순위                                                           | P3               |
| 1      | 겉모양 문제 — 여유가 있을 때                                                        | P3               |
| 0      | 사용성 문제가 아님                                                                  | finding에서 뺀다 |

심각도는 세 요소로 매긴다.

- **빈도**: 얼마나 많은 사용자가 겪는가
- **영향**: 겪었을 때 넘어서기 어려운가
- **지속성**: 한 번 알면 넘어가는가, 매번 막히는가

평가자 한 명의 심각도는 흔들린다. 에이전트는 흐름을 익히는 통과와 기록하는 통과를 나누고, 가능하면 다른 뷰포트나 다른 사용자 유형으로 한 번 더 통과해 심각도를 다시 매긴 뒤 평균을 낸다. 판단이 갈린 항목은 갈렸다고 적는다.

## 3. 범위와 정리

- 한 번에 과제 하나, 사용자 집단 하나, 기기 하나로 좁힌다.
- 모든 위반을 고칠 필요는 없다. 맥락 안에서 사용자 영향을 판단한다.
- 같은 원인의 여러 증상은 원인 하나로 묶고, 중복 finding은 합친다.

## 4. 이유를 설명하는 어휘 — Laws of UX

법칙은 finding이 아니라 finding의 이유다. 「힉의 법칙 위반」이라고 쓰지 말고 「선택지 14개가 한 화면에 나열돼 결정이 늦어진다(힉의 법칙)」처럼 쓴다.

| 법칙                                            | 리뷰에서 쓰는 곳                                                                       |
| ----------------------------------------------- | -------------------------------------------------------------------------------------- |
| 도허티 임계 (Doherty Threshold)                 | 약 400ms 안에 반응하지 않는 동작에 진행 표시·체감 성능 기법이 필요한 이유              |
| 힉의 법칙 (Hick's Law)                          | 선택지를 줄이거나 추천 하나를 강조하고 단계를 나누는 이유                              |
| 피츠의 법칙 (Fitts's Law)                       | 자주 누르는 대상을 크고 가깝게, 서로 떨어뜨려 두는 이유                                |
| 제이콥의 법칙 (Jakob's Law)                     | 다른 서비스에서 익힌 관례를 따르는 이유, 개편 뒤 적응 기간을 두는 이유                 |
| 테슬러의 법칙 (Tesler's Law)                    | 없앨 수 없는 복잡성을 사용자 대신 시스템이 떠안아야 하는 이유                          |
| 피크엔드 법칙 (Peak-End Rule)                   | 완료 화면과 오류 복구 화면을 먼저 다듬는 이유                                          |
| 목표 경사 효과 (Goal-Gradient Effect)           | 남은 단계와 진행률을 보여 주는 이유                                                    |
| 자이가르닉 효과 (Zeigarnik Effect)              | 끝나지 않은 일을 이어 하기 쉽게 보여 주는 이유                                         |
| 선택 과부하 (Choice Overload)                   | 비교할 기준과 추천을 함께 주는 이유                                                    |
| 폰 레스토프 효과 (Von Restorff Effect)          | 화면에서 주요 행동 하나만 강조하는 이유                                                |
| 계열 위치 효과 (Serial Position Effect)         | 핵심 메뉴·항목을 목록의 처음과 끝에 두는 이유                                          |
| 근접성·공통 영역 (Proximity · Common Region)    | 관련 있는 요소를 가깝게, 같은 카드·배경 안에 묶는 이유                                 |
| 청킹 (Chunking)                                 | 카드 번호·전화번호·긴 목록을 작은 묶음으로 나눠 보여 주는 이유                         |
| 심미적 사용성 효과 (Aesthetic-Usability Effect) | 보기 좋은 화면이 사용성 문제를 가릴 수 있어 과제 성공으로 확인하는 이유                |
| 앵커링·타협 효과 (Anchoring · Compromise)       | 요금제 표에서 비싼 안 옆의 가운데 안이 잘 팔리는 이유 — 기만 경계는 `ux-dark-patterns` |
