# 폼·가입·결제 점검

출처: GOV.UK Design System「Question pages」·「Error message」·「Error summary」·「Validation」, GOV.UK Service Manual「Structuring forms」(2016, 2018 갱신), Baymard Institute「Checkout UX 2025」(2024, 2025-11 갱신)·「Cart Abandonment Rate Statistics」(2025-09 갱신)·「Usability Testing of Inline Form Validation」(2024), NN/g Rachel Krause「10 Design Guidelines for Reporting Errors in Forms」(2019)·Katie Sherwin「Placeholders in Form Fields Are Harmful」(2014), 토스「Value first, Cost later」(2023), W3C WCAG 2.2. 수치는 표기한 시점의 값이다.

## 1. 질문을 묻기 전에

- 질문마다 왜 필요한지, 누가 답해야 하는지, 답을 어떻게 확인하는지, 어떻게 보호하는지 답한다. 답하지 못하면 그 질문을 뺀다.
- 자격을 가르는 질문을 앞에 두고, 해당하는 사람에게만 다음 질문이 보이게 분기한다.
- 한 화면에 질문 하나로 시작한다. 묶어도 된다는 근거가 있을 때만 합친다.
- 가치를 먼저 보여 주고 비용은 나중에 묻는다. 비용이 큰 요청은 질문 서너 개를 넘는 입력, 답하는 데 몇 초 넘게 생각해야 하는 질문, 민감한 정보다.
- 같은 과정에서 이미 받은 정보를 다시 입력하게 하지 않는다. 자동으로 채우거나 고르게 한다(WCAG 3.3.7).
- 뒤로 가기는 입력해 둔 상태를 그대로 되살린다.

## 2. 입력 칸

- 라벨은 늘 보이게 둔다. 플레이스홀더는 입력하면 사라져 라벨을 대신할 수 없다.
- 필수와 선택을 둘 다 표시한다. 한쪽만 표시하면 나머지를 추측하게 된다.
- 형식이 있으면 칸 아래 도움말로 예시를 보여 준다(「예: 010-1234-5678」).
- 모바일에서는 입력 종류에 맞는 키보드(`inputmode`)와 자동완성(`autocomplete`)을 쓴다.
- 로그인에서 비밀번호 붙여 넣기와 비밀번호 관리자를 막지 않는다. 기억이나 옮겨 적기만 요구하는 인증 단계에는 대안을 둔다(WCAG 3.3.8).

## 3. 오류 계약

- 메시지는 해당 칸 바로 아래에 둔다. 칸의 위치가 무엇이 틀렸는지 말해 주므로 문구는 어떻게 고치는지를 쓴다.
- 빈 칸에는 할 일을 쓰고(「이름을 입력해 주세요」), 그 밖에는 조건을 쓴다(「이름은 35자까지 쓸 수 있어요」).
- 상단 요약을 쓰면 요약 항목이 해당 칸으로 이동하는 링크이고, 요약과 칸의 문구가 같다. 요약만 두지 않는다.
- 웹에서는 오류가 있는 동안 문서 제목 앞에 「오류: 」를 붙여 화면 낭독기 사용자도 바로 알게 한다.
- 「유효하지 않습니다」·「잘못된 입력입니다」·「오류가 발생했습니다」·「필수 항목입니다」만 있는 문구와 감탄사·과한 사과를 쓰지 않는다.
- 입력값을 지우지 않는다.
- 색만으로 오류를 알리지 않는다. 아이콘과 문구를 함께 쓴다.
- 같은 칸에서 같은 오류가 세 번 넘게 나면 설계 문제다. 예시·도움 경로를 연다.
- 자격 미달과 서비스 장애는 입력 오류가 아니다. 별도 화면에서 이유와 다음 행동을 알린다.

## 4. 검증 시점 — 하나를 고르고 이유를 적는다

두 출처의 권고가 다르다. 리뷰에서 어느 쪽을 기준으로 삼았는지 밝힌다.

| 방식                                                       | 근거                                                                                                                                      | 맞는 곳                                           |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 제출할 때 검증                                             | GOV.UK: 칸을 떠날 때 검증하지 않고, 리서치로 도움이 확인될 때만 인라인 검증을 더한다                                                      | 공공 신청서, 긴 폼, 보조기기 사용자가 많은 서비스 |
| 칸을 떠날 때 검증, 고치는 순간 오류 제거, 제출할 때 재확인 | Baymard 2024: 입력 중에는 검증하지 않고, 칸을 떠나거나 고정 길이 칸이 다 찼을 때 검증하며, 맞게 고치면 바로 오류를 지우고 성공을 표시한다 | 커머스 결제, 회원가입                             |

공통 기준: 입력이 끝나기 전에는 오류를 띄우지 않는다.

## 5. 결제 점검

Baymard 2025 벤치마크에서 주요 미국·유럽 사이트가 실패한 비율이다. 높은 실패율은 흔한 실수라는 뜻이지, 괜찮다는 뜻이 아니다.

| 점검                                    | 실패한 사이트 |
| --------------------------------------- | ------------- |
| 비회원 결제가 가장 눈에 띄는 선택지인가 | 62%           |
| 비밀번호 규칙이 과하지 않은가           | 65%           |
| 필수와 선택 칸을 둘 다 표시했는가       | 61%           |
| 오류 메시지가 원인에 맞게 바뀌는가      | 94%           |
| 전화번호가 왜 필요한지 설명하는가       | 49%           |
| 배송 속도 대신 도착 날짜를 보여 주는가  | 48%           |

- 입력 칸 수: 이상적인 결제는 폼 요소 12\~14개, 입력 칸 7\~8개다. 미국 평균은 폼 요소 23.48개, 입력 칸 14.88개다.
- 결제 이탈 이유 상위(그냥 둘러본 경우 제외): 추가 비용 40% · 느린 배송 20% · 카드 정보에 대한 불신 19% · 가입 강요 18% · 너무 길거나 복잡함 17% · 사이트 오류 17%.
- 그래서 총액은 첫 화면부터 보여 주고, 계정 만들기는 결제 뒤로 미루고, 결제 단계 수와 입력 칸 수를 함께 센다.
- 마지막 단계에서 비용이 붙는 흐름은 사용성 문제이면서 기만 유형(순차 공개 가격 책정)이다. `ux-dark-patterns`로 넘긴다.
