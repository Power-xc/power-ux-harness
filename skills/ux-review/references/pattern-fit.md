# 패턴 쓰임 대조표

리뷰 대상의 요소를 패턴 이름으로 적은 뒤, 그 패턴이 지금 쓰임에 맞는지 이 표로 판정한다. 수정안도 같은 이름으로 쓴다. 「로딩 넣어 주세요」라고만 하면 대부분 스피너가 되고, 「피드백 강화」는 읽는 사람마다 다른 화면이 된다.

출처: NN/g Katie Sherwin「Progress Indicators Make a Slow System Less Insufferable」(2014)·Samhita Tankala「Skeleton Screens 101」(2023)·Alita Kendrick「Toggle-Switch Guidelines」(2018)·Angie Li「Date-Input Form Fields」(2017)·Aurora Harley「Slider Design: Rules of Thumb」(2015)·Jakob Nielsen「Confirmation Dialogs Can Prevent User Errors」(2018)·Page Laubheimer「Executing UX Animations」(2020)·Aurora Harley「Icon Usability」(2014)·Hoa Loranger「Infinite Scrolling Is Not for Every Website」(2014), Buell·Norton「The Labor Illusion」(Management Science, 2011), 토스「좋은 에러 메시지를 만드는 6가지 원칙」(2022), Google Material Design 3의 Snackbar·Dialogs·Bottom sheets 지침, W3C WCAG 2.2와 Understanding 2.2.1·4.1.3. 원문 문장을 옮기지 않고 요약했다.

## 1. 알림·피드백 — 방해 수준

방해 수준은 알림이 사용자의 흐름을 얼마나 붙잡는지다. 정보의 무게와 되돌릴 수 있는지에 맞춰 가장 낮은 수준을 고른다.

| 수준 | 성격                                | 패턴                                  | 쓰는 때                                                                                                                 | 이렇게 쓰면 finding                                                                                                                                                                                                                                         |
| ---- | ----------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | 사용자가 볼 때만 보임               | 뱃지 · 툴팁                           | 확인하지 않은 새 소식(뱃지) · 숫자나 용어의 기준 보충(툴팁)                                                             | 개수가 의미 없는데 숫자를 씀(점이면 충분) · 요금·제약·마감을 툴팁에만 둠 · 오류를 툴팁으로 알림                                                                                                                                                             |
| 1    | 비차단, 몇 초 뒤 사라짐             | 토스트 · 행동 없는 스낵바             | 저장·복사처럼 이미 끝난 일의 결과                                                                                       | 버튼을 넣음 · 실패나 설명이 필요한 내용을 몇 초 만에 사라지는 알림에 담음 · 웹에서 같은 정보를 화면 어디에도 남기지 않음                                                                                                                                    |
| 2    | 비차단, 해결하거나 닫을 때까지 머묾 | 행동 있는 스낵바 · 배너 · 인라인 오류 | 되돌릴 기회 하나(스낵바) · 마감·점검처럼 계속 보여야 하는 정보(배너) · 입력 오류(인라인)                                | 스낵바에 행동 둘 이상 · 행동 있는 스낵바가 시간이 지나면 사라짐 · 핵심 작업으로 가는 유일한 길이 스낵바 · 닫을 수 없는 배너(필수 고지 제외) · 한 번 보면 되는 결과를 배너로 띄움 · 오류를 폼 상단이나 토스트로만 알림                                       |
| 3    | 차단, 답하거나 닫아야 진행          | 모달 바텀시트 · 코치마크 · 대화상자   | 지금 화면을 둔 채 행동 하나 고르기(바텀시트) · 첫 방문의 핵심 기능 하나(코치마크) · 되돌리기 어려운 결정 직전(대화상자) | 파괴적 항목이 위쪽이거나 구분되지 않음 · 바텀시트를 끌어야만 닫힘 · 코치마크 여러 개 · 바로 닫을 수 없음 · 대화상자 행동 셋 이상 · 「정말 ~하시겠어요?」 같은 제목 · 확인 버튼이 「확인」 · 되돌릴 수 있는 일에 확인 대화상자 · 자주 떠서 읽지 않고 닫게 됨 |

판정 순서:

1. 정보가 사용자의 다음 결정을 바꾸지 않으면 수준 0~1을 쓴다.
2. 되돌릴 기회를 주거나 해결될 때까지 보여야 하면 수준 2를 쓴다.
3. 되돌릴 수 없는 결정 직전에만 수준 3으로 멈춘다. 되돌리기를 만들 수 있으면 확인 대화상자보다 스낵바의 되돌리기와 일정 기간 복구(휴지통)를 우선한다.
4. 확인 대화상자는 행동을 묻는 제목(「구독을 해지할까요?」)과 결과 한 줄로 쓰고, 버튼은 둘까지, 확인 쪽은 결과 동사(「해지하기」·「삭제」)로 쓴다. 확인 쪽을 기본 선택으로 두지 않는다. 이름을 직접 입력하게 하는 식의 의도적 동작은 가장 위험한 일에만 쓴다.
5. 모달 바텀시트는 처음에 화면 높이의 절반 이하로 열고, 끌지 않아도 닫히게(닫기 버튼·바깥 누르기) 한다.

접근성 대조: 토스트·스낵바 같은 상태 메시지는 포커스를 옮기지 않고도 보조기기가 읽도록 `role="status"`로 알린다. 급하지 않은 내용에 `role="alert"`나 `aria-live="assertive"`를 쓰면 실패다(WCAG 4.1.3). 스스로 사라지는 알림은 시간 제한이다. 같은 정보를 화면의 다른 곳에서도 찾을 수 있을 때만 자동으로 사라지게 하고, 행동이 있는 스낵바는 누르거나 닫을 때까지 남긴다(WCAG 2.2.1, Material 3 스낵바 지침).

## 2. 로딩 — 기다림의 길이와 모양

같은 시간을 기다려도 무엇을 보여 주느냐에 따라 체감 속도가 달라진다(지각된 성능). 실제 속도를 줄일 수 없을 때 아래에서 기다림에 맞는 모양을 고른다.

| 기다림               | 패턴                    | 기준                                                                            |
| -------------------- | ----------------------- | ------------------------------------------------------------------------------- |
| 약 1초 미만          | 표시 없음               | 스피너·스켈레톤이 깜빡임만 만든다                                               |
| 약 2~10초            | 스피너(반복 애니메이션) | 카드·영상처럼 한 영역이 늦을 때                                                 |
| 10초 미만 전체 화면  | 스켈레톤                | 레이아웃이 정해진 피드·카드. 내용 자리 없는 빈 틀만 그리면 멈춘 화면으로 보인다 |
| 약 10초 이상         | 진행 바·진행 링(%)      | 남은 양이나 시간을 보여 준다. 좁은 자리는 진행 링                               |
| 업로드·변환·내려받기 | 진행 바 또는 단계 표시  | 스켈레톤을 쓰지 않는다                                                          |
| 여러 단계 흐름       | 단계 표시               | 가입·결제에서 현재 단계와 전체 단계 수                                          |
| 큰 이미지            | 블러 업                 | 저해상도 미리보기 후 선명하게                                                   |
| 실패가 드문 동작     | 낙관적 UI               | 좋아요·저장을 먼저 반영하고, 실패하면 되돌리며 알린다                           |
| 긴 생성              | 스트리밍 텍스트         | 생성되는 대로 보여 주고 중지 버튼을 둔다                                        |
| 누른 직후            | 로딩 버튼               | 누른 버튼 자리에서 처리 중을 보이고 중복 제출을 막는다                          |
| 검색·견적·매칭       | 진행 과정 보이기        | 실제로 거치는 조회·비교 단계를 보여 준다(노동 착시). 꾸민 단계는 기만이다       |

## 3. 입력 — 고르는 방식과 컨트롤

| 할 일                  | 패턴             | 이렇게 쓰면 finding                                                                |
| ---------------------- | ---------------- | ---------------------------------------------------------------------------------- |
| 글자 입력              | 텍스트 필드      | 라벨 없이 플레이스홀더만 있음                                                      |
| 입력 검증              | 인라인 검증      | 입력을 마치기 전에 오류를 띄움 · 상단 요약만 있고 칸 옆 메시지가 없음              |
| 켜고 끄기              | 스위치           | 저장 버튼이 있는 폼 안의 스위치(스위치는 즉시 적용을 약속한다 — 체크박스로 바꾼다) |
| 여러 개 고르기         | 체크박스         | 하나만 골라야 하는데 체크박스를 씀                                                 |
| 하나만 고르기          | 라디오           | 선택지가 몇 개 안 되는데 셀렉트에 숨김                                             |
| 많은 선택지에서 하나   | 셀렉트           | 두세 개뿐인데 열어야 보임                                                          |
| 몇 개의 배타 보기 전환 | 세그먼트 컨트롤  | 실행 동작을 세그먼트에 넣음                                                        |
| 범위의 대략 값         | 슬라이더         | 정확한 값이 중요한데 슬라이더만 있음(직접 입력으로 바꾼다)                         |
| 작은 정수 증감         | 스테퍼           | 큰 수를 ±로만 입력하게 함                                                          |
| 가까운 날짜            | 달력형 날짜 선택 | 생일처럼 먼 날짜를 달력으로만 고르게 함(직접 입력이 빠르다)                        |

검증 시점과 오류 문구 계약은 [`forms-checkout.md`](./forms-checkout.md)를 따른다.

## 4. 내비게이션·제스처·아이콘·모션

- **끝 신호**: 목록 끝, 더 없음, 마지막 단계에 신호가 있는지 본다. 끝을 모르면 사용자는 계속 내리거나 멈출 곳을 잃는다.
- **무한 스크롤**: 둘러보기 피드에는 맞지만, 특정 항목 찾기·비교·되돌아가기가 목표인 화면에는 페이지네이션이나 필터·정렬이 맞다.
- **가변 보상 루프**: 당겨서 새로고침처럼 당길 때마다 결과가 달라지는 장치는 습관을 만든다. 사용자의 목표를 해치는 반복 사용을 유도하는지, 멈출 지점이 있는지 본다.
- **보이지 않는 제스처**: 밀어서 삭제·길게 누르기·드래그는 화면에 보이지 않는다. 같은 기능을 버튼이나 메뉴에도 둔다. 끌기 동작에는 한 번 누르기 대안이 필요하다(WCAG 2.5.7).
- **아이콘**: 집·검색·인쇄처럼 널리 통하는 아이콘은 드물다. 그 밖의 아이콘에는 늘 보이는 텍스트 라벨을 붙인다. 이미 관습이 된 아이콘은 실물과 닮지 않았다는 이유로 바꾸지 않는다.
- **모션**: 방향만 말하지 말고 이름과 시간을 쓴다. 대부분의 UI 전환은 100\~500ms, 체크·토글 같은 작은 반응은 약 100ms, 대화상자 등장은 200\~300ms가 기준이다. 들어오는 요소는 이즈 아웃, 나가는 요소는 이즈 인 계열을 쓰고 나가는 쪽을 조금 짧게 한다. 「부드럽게」는 이즈 아웃, 「튕기게」는 스프링이다. 움직임 줄이기 설정(`prefers-reduced-motion`)을 따르는지 본다.

## 5. 결정 과제로 패턴 고르기

경쟁 제품에 있다는 사실은 근거가 아니다. 사용자가 무엇을 결정하는지 먼저 적는다.

| 결정 과제                                | 맞는 장치                                           |
| ---------------------------------------- | --------------------------------------------------- |
| 같은 상품을 파는 많은 판매자를 빨리 비교 | 별점·가격·배송처럼 숫자로 비교하는 장치, 정렬·필터  |
| 이미 골라 둔 소수 중에서 믿고 고름       | 자세한 후기·고른 이유·큐레이션 근거                 |
| 처음 써 보는 기능을 이해                 | 빈 상태의 다음 행동, 코치마크 하나                  |
| 되돌릴 수 없는 결정                      | 결과를 말하는 확인 대화상자, 결정 전 요약           |
| 요금제 여러 개 중 하나를 고름            | 같은 항목·단위로 맞춘 비교표, 기준을 적은 추천 하나 |

AI 응답 화면의 패턴(스트리밍·중지·출처·다시 생성)은 `ux-ai`, 결제·구독 화면의 심리 장치와 기만 경계는 `ux-dark-patterns`가 판정한다.

## 6. 요금제·가격표

요금제 표는 사용자가 「나에게 맞는 것」을 고르는 화면이다. 가운데가 잘 팔리는 이유(앵커링·타협 효과)를 알고 쓰되, 장치보다 비교가 먼저다. 장치별 정직한 쓰임과 기만의 선은 `ux-dark-patterns`의 [`decision-devices.md`](../../ux-dark-patterns/references/decision-devices.md) 가격표 장치 표를 따른다.

| 요소       | 기준                                                                                | 이렇게 쓰면 finding                                                     |
| ---------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 요금제 수  | 2~4개. 사용자 집단이 실제로 나뉘는 만큼만                                           | 차이를 설명할 수 없는 요금제 · 5개 이상을 한 줄에 나열(선택 과부하)     |
| 비교 항목  | 모든 요금제가 같은 항목을 같은 순서·같은 단위로. 다른 점을 위에, 같은 점은 접는다   | 요금제마다 항목·단위가 다름 · 빠진 항목을 빈칸으로 둬 「없음」인지 모름 |
| 추천 강조  | 하나만 강조하고 「2명 이상이 쓰면」처럼 누구에게 맞는지 쓴다(폰 레스토프 효과)      | 강조가 둘 이상 · 기준 없는 「추천」 · 집계 없는 「가장 인기」           |
| 가격 표시  | 실제로 청구되는 금액·주기를 가장 크게. 환산가(월·하루)는 보조로                     | 환산가만 크게 · 연 결제의 일시 청구액이 작은 글씨                       |
| 월·연 전환 | 전환 스위치 옆에 아끼는 금액을 원 단위로. 기본값은 사용자 대부분이 고르는 주기      | 기본값을 연 결제로 두고 청구 시점을 숨김                                |
| 할인가     | 판매한 적 있는 정가에만 취소선과 할인율                                             | 늘 할인 중인 가격 · 근거 없는 정가                                      |
| 다음 행동  | 요금제마다 같은 무게의 가입 버튼, 무료 체험이면 유료 전환 날짜와 금액을 버튼 근처에 | 한 요금제에만 버튼 · 체험 종료 후 금액을 다른 화면에서만 알림           |

가운데 요금제의 선택 비율만 올리는 수정은 성공이 아니다. `ux-metrics`로 요금제 구성을 바꿀 때 30일 안 하향·환불·해지와 요금 문의를 가드레일로 함께 잰다.
