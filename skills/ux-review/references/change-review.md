# 변경 리뷰 — 이번 변경이 화면을 나쁘게 했나

출처: jakubkrehel/skills(커밋 6c21201, MIT)의 `interface-review`(SKILL.md·scope-resolution.md·removed-signals.md)와 `better-interface`(SKILL.md·review-format.md). 원문 문장을 복사하지 않고 이 하네스의 절차에 맞게 다시 썼다. 판정은 `ux-review`의 PASS/FAIL과 finding 표를 쓰고, 원본의 Block/Approve와 보고 표는 가져오지 않았다. `word-break` 단서(한글 줄바꿈)는 한국어 화면 기준으로 더했다.

PR·브랜치·커밋 범위·작업 중 변경을 리뷰할 때 쓴다. 작성자가 묻는 것은 「내가 더 나쁘게 만들었나」다. 변경이 만든 것을 보고하고, 원래 있던 것은 짧게만 적는다. 원래 있던 문제 3개는 배려이고 30개는 아무도 요청하지 않은 다른 리뷰다.

diff 전체를 읽은 뒤 판단한다. 훑어 읽으면 다음 hunk가 이미 고친 것을 finding으로 낸다. 정확성·테스트·보안·성능은 프로젝트의 일반 코드 리뷰 몫이다. 그런 문제를 보면 한 번 이름만 대고 넘어간다.

## 1. 범위 정하기

대상은 받은 그대로 쓴다: `pr <n>`, 브랜치, ref, 커밋 범위, `working`, `staged`. 사용자가 범위를 점으로 적었으면 그 점을 그대로 쓴다. `<a>..<b>`는 두 끝을 비교하고 `<a>...<b>`는 `<a>`와 `<b>`의 merge-base부터 `<b>`까지를 비교한다. 브랜치는 기본 브랜치와의 merge-base 기준으로 점 세 개를 쓴다. 점 두 개는 기본 브랜치에 들어온 남의 커밋까지 변경으로 센다.

대상이 없으면 아래 순서로 처음 맞는 것을 고른다.

1. `HEAD`가 `git merge-base origin/<기본 브랜치> HEAD`보다 앞서 있다. 그 범위와 커밋 안 한 변경을 함께 리뷰하고, 커밋 수와 파일 수를 따로 적는다.
2. 작업 트리에 변경이 있다. 그 변경을 리뷰한다.
3. 둘 다 아니다. 리뷰할 변경이 없다.

③에서 스스로 `HEAD~1..HEAD`로 넘어가지 않는다. 마지막 커밋은 병합이거나 남의 작업일 수 있다. 사실을 먼저 말한다: 현재 브랜치, 기준보다 앞선 커밋 수, 작업 트리 상태, 마지막 커밋의 짧은 SHA와 제목, 열린 PR(`gh pr status`). `gh pr status`는 PR이 없어도 성공하고 `currentBranch`만 비어 있다. `gh`가 없거나 인증이 없거나 GitHub 원격이 없으면 실패한다. 실패하면 「PR을 찾지 못함」이라고 말하고 나머지 길을 낸다. 그다음 사용자가 고르게 한다.

- 현재 브랜치의 열린 PR. 있으면 먼저 낸다. 이미 병합된 브랜치라도 사용자가 뜻한 것은 그 PR이다.
- 마지막 커밋. 짧은 SHA와 제목을 함께 보여 준다.
- 사용자가 지정할 대상(`pr <n>`, 브랜치, ref, 범위).
- 저장소 전체 화면 리뷰. 변경 리뷰가 아니므로 상태 열과 「원래 있음」 절 없이 `ux-review` 일반 절차로 돌린다.

제외로 범위가 비었으면 제외한 파일 이름을 함께 말한다. 기준 커밋은 `$BASE`로 기록하고 보고 머리에 적는다. 이 문서의 모든 명령이 `$BASE`를 쓴다.

**기본 브랜치 찾기.** `refs/remotes/origin/HEAD`를 먼저 보고, 없으면 `gh repo view --json defaultBranchRef`를 본다. 그래도 없으면 `git remote set-head origin --auto`로 원격에 묻는다(네트워크가 필요하고 `.git` 아래 ref만 쓰므로 허용되며, 검증 항목에 적는다). 원격이 아예 없으면 로컬 `main`이나 `master`를 쓰고 어느 쪽을 가정했는지 적는다.

**커밋 안 한 변경.** `git diff HEAD`는 추적 중인 파일만 보여 준다. 커밋 안 한 변경이 범위에 들면 `git ls-files --others --exclude-standard`를 함께 돌린다. 안 그러면 새로 추가한 컴포넌트가 범위에서 조용히 빠진다.

**PR.** 머리를 원격 추적 ref로 받아 그 자리에서 읽는다. 포크에서도 된다.

```bash
git fetch origin "pull/<n>/head:refs/remotes/pr/<n>"
git show refs/remotes/pr/<n>:경로/파일
```

- 기준은 PR 자신의 기준 브랜치다. 기본 브랜치로 가정하지 않는다. `gh pr view <n> --json baseRefName,baseRefOid`로 읽고 로컬에 없으면 받는다. `release/2.0` 대상 PR을 `main`과 비교하면 두 브랜치 사이의 모든 커밋이 섞인다.
- 작업 트리의 파일은 다른 리비전이라 열지 않는다.
- `gh pr diff <n>`은 패치 글만 빨리 볼 때 쓴다. 바뀌지 않은 앞뒤 맥락을 읽거나 소비처로 펼칠 수 없으니 ref도 받는다.
- 인용 줄 번호는 받은 ref 기준이다. 보고 머리에 머리 ref와 SHA를 적어 번호가 맞게 한다.
- `gh pr view`의 `title`과 `body`가 6절의 말한 의도다. 본문이 비었으면 커밋 제목을 쓴다.

**이상한 저장소 상태.** 셋을 따로 다룬다. 그 밖(관계없는 이력, 커밋 없는 저장소, 서브모듈 포인터 이동)은 `merge-base`에서 소리 내어 실패한다. 기준을 풀 수 없다고 말하고 멈춘다. 이름을 못 대는 범위는 리뷰하지 않는다.

| 상태                          | 처리                                                                                                                                                                                                                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 분리된 HEAD                   | 기본 브랜치와의 merge-base를 쓰고 보고 머리에 SHA를 적는다                                                                                                                                                                                                                                        |
| 얕은 복제(CI 기본)            | `merge-base`가 비면 `--deepen=50`으로 받고 다시 시도, 그다음 `--deepen=200`, 그래도 안 되면 범위를 풀 수 없다고 보고한다. `.git`만 쓰므로 허용되며 검증 항목에 적는다                                                                                                                             |
| 리베이스·병합 중(조용히 틀림) | `git diff`가 성공하지만 변경이 아닌 것을 돌려줘 리뷰가 멀쩡해 보이고 틀린다. `git rev-parse --git-path`로 `rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`를 확인한다. `.git/` 경로를 직접 검사하지 않는다(연결된 워크트리에서는 폴더가 아니다). 작업 중이면 멈추고 그렇게 말한다 |

**이름 바뀐 파일.** `git diff`는 이름 변경을 기본으로 찾고 `--name-status`는 `R100 옛경로 새경로`로 적는다. 이름을 바꾸면서 고친 파일은 `--find-renames=40%`로 기준을 낮춘다. 이름 변경은 이동 하나로 리뷰한다(삭제와 추가로 세지 않는다). 이동 뒤 그대로인 코드는 바뀌지 않은 코드이고 실제로 고친 줄만 범위다.

## 2. 빼는 파일

기계가 쓴 파일은 화면 기준이 닿지 않는다. 빼고 무엇을 뺐는지 보고 머리에 적는다.

| 분류            | 패턴                                                                                                                                                 |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 잠금 파일       | `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `bun.lockb`, `Cargo.lock`, `composer.lock`, `Gemfile.lock`, `poetry.lock`, `uv.lock` |
| 스냅숏·픽스처   | `__snapshots__/`, `*.snap`, `*.approved.*`, `test-results/`, `playwright-report/`                                                                    |
| 빌드 결과       | `dist/`, `build/`, `out/`, `.next/`, `.turbo/`, `.svelte-kit/`, `coverage/`, `storybook-static/`, `*.min.js`, `*.min.css`, `*.map`                   |
| 생성 코드       | `*.gen.ts`, `*.generated.*`, 빌드가 내보낸 `*.d.ts`, GraphQL·Prisma 클라이언트 출력                                                                  |
| vendor          | `vendor/`, `third_party/`, `node_modules/`                                                                                                           |
| 바이너리·미디어 | `*.png`, `*.jpg`, `*.webp`, `*.avif`, `*.woff2`, `*.mp4`, `*.pdf`                                                                                    |

예외 둘은 범위에 남긴다. 새로 넣거나 바꾼 글꼴 파일은 글자 변경이고, 컴포넌트에 더한 이미지는 외곽선과 대체 글의 변경이다. 바이트는 보지 않고 그것을 참조하는 코드를 본다.

제외는 pathspec으로 걸어 보고 머리의 파일 수가 실제로 리뷰한 수가 되게 한다.

```bash
git diff --name-only "$BASE" <head-ref> -- . ':(exclude)pnpm-lock.yaml' ':(glob,exclude)**/dist/**'
```

조용히 덜 빼는 함정이 둘이다. `*.lock`은 `yarn.lock`·`Cargo.lock`은 잡지만 `package-lock.json`과 `pnpm-lock.yaml`은 못 잡는다. 표의 이름을 하나씩 다 쓴다. `glob` 없는 `**/dist/**`는 앞에 `/`가 있어야 해서 루트의 `dist/`를 놓친다. pathspec을 넣고 빼고 두 번 돌려 파일 수가 이름 댄 만큼만 줄었는지 확인한다.

빼고 남은 것이 없으면 변경 없음이다. 빈 리뷰를 PASS로 내지 않는다.

## 3. 바뀐 파일이 그려지는 화면을 본다

바뀐 파일은 증거일 뿐 리뷰 대상이 아니다. 그 파일이 그려지는 화면(영향 범위)을 리뷰한다.

- 기본은 1단계, 곧 바로 가져다 쓰는 곳과 호출하는 곳이다. 프로젝트 자체의 해석기가 있으면 그것을, 없으면 import 경로를 쓴다.
- 디자인 토큰·테마 값·공용 기본 컴포넌트는 한 줄이 제품 전체에 닿으므로 2단계까지 펼친다.
- 펼치는 소비처는 두 단계를 합쳐 5곳까지다. 순서는 다시 돌려도 같도록 규칙으로 정한다: ① 경로·레이아웃 진입점(`app/**/page.*`, `app/**/layout.*`, `pages/**`, `routes/**`, `src/views/**`, `*.astro` 페이지) ② 가져다 쓰는 파일 수가 많은 것 ③ 같은 패키지·기능 폴더. 어느 지점부터 임의였으면 그렇게 말한다.
- 안 펼친 소비처의 수를 적는다. 말하지 않은 끊김은 빠짐없이 봤다는 뜻으로 읽힌다.
- `git grep <패턴> <ref>`로 그 ref에서 찾는다. ref를 안 주면 작업 트리를 찾아 PR 변경이 만든 소비처를 놓친다. 결과는 `<rev>:경로` 꼴이며 `git show <ref>:경로`로 읽는다. 패턴이 대시로 시작하면(`--color-*` 토큰) `-e`를 붙인다.
- 토큰은 파일 대신 토큰 이름으로 찾는다. 소비처는 이름을 참조하고 파일을 가져오지 않는다.

## 4. 지워진 줄 읽기

회귀는 바뀐 뒤 상태에서 보이지 않는다. 모든 hunk의 `-` 쪽을 아래 단서 표로 훑는다.

| `-` 쪽에서 사라진 것                                                                              | 판단하는 곳                    | 확인할 것                                                      |
| ------------------------------------------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------- |
| `aria-label`, `aria-labelledby`, `aria-describedby`, `aria-live`, `role=`                         | `ux-a11y`                      | 컨트롤·영역이 이름·설명·알림을 잃었나                          |
| `alt=`, `<label`, `for=`, `htmlFor`, `scope=`                                                     | `ux-a11y`                      | 이미지·입력 칸·표 칸이 프로그램상 연결을 잃었나                |
| `<button>`, `<a>`, `<nav>`, `<main>`, `<ul>`이 `div`·`span`으로 바뀜                              | `ux-a11y`                      | 꾸밈을 얻으려고 키보드·보조기기 동작을 내줬나                  |
| `:focus-visible`, `:focus`, `outline`, `tabindex`                                                 | `ux-a11y`                      | 키보드 사용자가 포커스 표시를 잃거나 탭 순서에서 빠졌나        |
| `prefers-reduced-motion`                                                                          | `ux-a11y`                      | 움직임이 시스템 설정을 무시하게 됐나                           |
| `prefers-contrast`                                                                                | `ux-spec`의 `visual-color.md`  | 색이 대비 설정을 무시하게 됐나                                 |
| 논리 속성이 `left`·`right`로 바뀜                                                                 | `ux-spec`의 `visual-layout.md` | 방향에 따라 바뀌는 배치를 버렸나                               |
| `lang=`, `dir=`                                                                                   | `ux-spec`의 `visual-type.md`   | 언어 정보나 글 방향을 버렸나                                   |
| `text-wrap`, `line-clamp`, `overflow-wrap`, `word-break`, `tabular-nums`, `font-feature-settings` | `ux-spec`의 `visual-type.md`   | 글 그리기·줄바꿈(한글 줄바꿈 포함)·숫자 정렬이 조용히 바뀌었나 |
| 색 토큰이 리터럴로, 또는 더 옅은 토큰으로 바뀜                                                    | `ux-spec`의 `visual-color.md`  | 그려지는 대비 짝이 이제 실패할 수 있다. 재 본다                |
| 사용자에게 보이는 문구가 지워지거나 줄어듦                                                        | `ux-writing`                   | 라벨·오류·빈 상태가 담던 정보를 잃었나                         |

단서는 finding이 아니라 출발점이다. 같은 변경 안에서 대체한 것이 없을 때만 회귀다. 판단하는 곳의 기준으로 확인된 것만 보고하고 상태는 회귀로 둔다.

**같은 것으로 인정하는 대체.** 아래에 해당하면 단서를 버린다.

- `aria-label`이 보이는 글을 가리키는 `aria-labelledby`로 바뀜
- `div`가 기본 요소가 되어 명시한 `role`을 뺌(`role="button"`이 빠지고 `<button>`이 됨)
- `outline`이 같은 `:focus-visible` 선택자의 `box-shadow` 링으로 바뀜
- 이미 기본으로 포커스되는 요소에서 `tabindex="0"`을 뺌
- 색 리터럴이 같은 값의 토큰으로 바뀜
- 물리 속성이 논리 속성으로 바뀜(고침이므로 회귀로 세지 않는다)
- 문구가 번역 파일로 이동함(삭제가 아님)

**찾는 명령.** `-` 줄만 걸러 `+` 줄이 가리지 못하게 한다. 2절의 제외 pathspec을 `--` 뒤에 붙인다.

```bash
git diff -U0 "$BASE" <head-ref> -- . <exclusions> \
  | grep -E '^-' | grep -vE '^--- (a/|/dev/null)' \
  | grep -E 'aria-|role=|alt=|htmlFor|for=|scope=|focus|outline|tabindex|prefers-|lang=|dir=|text-wrap|line-clamp|overflow-wrap|word-break|tabular-nums|font-feature|inset-|-inline|-block'
```

커밋 안 한 변경이 범위에 들면 `<head-ref>`를 빼서 작업 트리와 비교한다. 지운 문구와 색 토큰 교체는 패턴이 없으니 hunk를 읽는다. `-U0`은 앞뒤를 숨기므로, 판단하기 전에 hunk 둘레를 읽는다. 지워진 속성은 그것이 붙어 있던 요소 없이는 뜻이 없다.

## 5. 원인으로 상태 붙이기

모든 finding에 상태 하나를 붙인다.

| 상태      | 영어         | 뜻                                    |
| --------- | ------------ | ------------------------------------- |
| 새로 생김 | Introduced   | 이번 변경이 만들었다                  |
| 회귀      | Regression   | 이번 변경이 멀쩡하던 것을 약하게 했다 |
| 원래 있음 | Pre-existing | 변경 전부터 있었고 더 나빠지지 않았다 |

위치가 아니라 원인으로 붙인다. 바뀐 줄이 일으킨 문제는 어디에 나타나든 새로 생김이나 회귀다. 바뀐 토큰 때문에 손대지 않은 화면에 생긴 문제도 그렇다. 변경이 만들지도 키우지도 않은 문제는 바뀐 줄 세 줄 옆에 있어도 원래 있음이다.

줄이 변경 전부터 있었는지는 리뷰 범위에 blame을 걸어 확인한다. 맨 앞 `^`는 기준 이후 바뀌지 않은 줄이다.

```bash
git blame -L <줄>,<줄> "$BASE"..<head-ref> -- 경로/파일
```

커밋 안 한 변경은 범위를 빼고 돌린다. `Not Committed Yet`로 나오거나 `$BASE..HEAD` 안의 커밋으로 나온 줄은 변경에 속한다.

PASS/FAIL 판정과 P1 셈은 새로 생김·회귀만 센다. 원래 있음뿐이면 PASS다. 원래 있음은 최대 3개까지, 높은 순으로 적고 「이번 변경 책임 아님」이라고 밝힌다.

## 6. 변경이 말한 의도와 맞추기

PR 제목·본문·연결 이슈·커밋 메시지를 읽고 화면이 그것을 해냈는지 본다. 화면 리뷰는 있는 상태만 보므로 없는 상태를 놓친다. 덜 끝난 변경은 이렇게 드러난다.

- 새 변형·크기·테마가 hover·focus·active·disabled·로딩·선택 중 일부 상태에만 적용됐다.
- 새 화면 문구가 프로젝트가 관리하는 번역 파일에 없다.
- 새 컴포넌트에 빈·로딩·오류·비활성·좁은 폭 상태가 없다.
- 형제 화면에는 있는 컨트롤을 한 화면에만 더했다.

범위가 넓다는 것은 진행 문제라 finding이 아니다.

## 7. 작업 트리를 바꾸지 않는다

변경 리뷰는 읽기 전용이다. `git fetch`(`.git`만 씀)는 허용한다. `gh pr checkout`·`git checkout`·`git switch`·`git stash`는 작성자가 열어 둔 파일을 바꾸니 쓰지 않는다. PR ref를 받아 그 자리에서 읽는다.

화면을 띄워 보는 것은 선택이다. 프로젝트에 값싼 미리보기가 있거나 사용자가 원할 때만 한다. `working`과 `branch`는 지금 체크아웃이 머리라 그대로 띄운다. 그 밖의 대상은 저장소 밖 임시 폴더에 `git worktree add`로 따로 띄우고 끝나면 지운다(`git worktree add "$TMPDIR/review-<n>" refs/remotes/pr/<n>`). 띄우지 않았으면 시각·동작 주장은 「확인 못 함」으로 적는다.

## 8. 보고

머리 표로 연다.

| 항목                    | 값                                                              |
| ----------------------- | --------------------------------------------------------------- |
| 대상                    | `branch`, `working`, `staged`, `pr 482` 또는 입력한 범위        |
| 기준 ref와 SHA          | `origin/main` — `a1b2c3d`                                       |
| 머리 ref와 SHA          | `refs/remotes/pr/482` — `e4f5a6b`                               |
| 커밋 수·커밋 안 한 파일 | 커밋 7개, 커밋 안 한 파일 2개                                   |
| 범위 파일 수            | 제외 뒤 12개                                                    |
| 제외                    | `pnpm-lock.yaml`, `src/__snapshots__/`                          |
| 펼친 화면·안 펼친 수    | `CheckoutPage`, `SettingsPanel` — `Button` 소비처 3곳은 안 펼침 |

그다음 `ux-review`의 finding 표에 `status` 열(새로 생김 · 회귀 · 원래 있음)을 더한 표를 낸다. 새로 생김·회귀가 없으면 표를 빼고 「이번 변경이 만든 화면 문제 없음」이라고 쓴다.

그다음 원래 있음을 최대 3개, 높은 순으로 짧은 표에 적는다. 열은 `priority`, 영역, `location`, 문제다. 없으면 절을 뺀다.

영역별로 증거가 없으면 「변경 범위에 근거 없음」이라고 쓴다. 이것은 범위 진술이고 빠짐이 아니다.

## 9. 끝내기 전 확인

| 실수                                                                           | 고침                                                            |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| `HEAD`가 merge-base보다 앞서 있는데 머리 표가 커밋 안 한 파일만 셈             | 브랜치 범위와 커밋 안 한 변경을 함께 리뷰하고 두 수를 다 적는다 |
| 사용자가 고르지 않은 `HEAD~1..HEAD` 리뷰                                       | 사실을 말하고 1절의 길을 낸 뒤 기다린다                         |
| 바뀐 공용 컴포넌트인데 펼친 화면에 소비처가 없음                               | 소비처로 펼치고 건너뛴 곳의 수를 적는다                         |
| 지워진 `aria-label`·`outline`·`prefers-reduced-motion`에 finding도 메모도 없음 | 4절 단서 표로 판단하는 곳에 넘긴다                              |
| 지운 속성이 같은 diff 다른 곳에 다시 나오는데 회귀로 적음                      | 같은 것으로 인정하는 대체를 먼저 본다                           |
| 바뀐 토큰을 쓰는 손대지 않은 화면의 문제를 원래 있음으로 적음                  | 변경이 원인이니 새로 생김이나 회귀다                            |
| hunk 밖의 줄을 원인 변경 없이 새로 생김으로 적음                               | 리뷰 범위에 blame을 건다                                        |
| 명령 기록에 `gh pr checkout`이나 `git switch`가 있음                           | ref를 받아 `git show`로 읽는다                                  |
| 인용한 줄이 `git show <머리 ref>:경로`와 맞지 않음                             | 보고 머리에 적은 머리 ref 기준으로 인용한다                     |
