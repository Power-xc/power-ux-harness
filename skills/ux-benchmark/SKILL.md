# UX Benchmark

같은 기능도 서비스의 맥락이 다르면 정답이 바뀐다. 다른 서비스에 있다는 사실은 근거가 아니다. 그 해법이 왜 거기서 통했는지, 그 이유가 우리에게도 있는지가 근거다.

## Trigger

- `@ux benchmark <상황|기능>`: 맥락 카드 → 비교 서비스 조사 → 인사이트 → 맥락별 제안
- `@ux context <서비스>`: 맥락 카드와 상황·예외 지도만
- 「비슷한 서비스는 이거 어떻게 해?」, 「잘된 곳 사례 찾아서 우리한테 맞게 제안해 줘」, 「벤치마킹해 줘」, 「60대 사용자가 늘었는데 이 화면 어떻게 바꿔야 해?」, 「이 기능을 넣을지 다른 데는 어떻게 했는지 봐 줘」

## Input

- `service`: 서비스 설명, 주소, 기획서, 화면
- `situation`: 설계할 상황이나 기능 하나(예: 처음 보내는 계좌로 큰돈 송금). 없으면 실수 비용이 가장 큰 상황 하나를 골라 `가정`으로 적는다.
- `context`(선택): 이미 아는 단계·사용자 수·사업 방식·타깃·연령·기기·지역·규제
- `comparables`(선택): 보라고 준 서비스. 없으면 직접 고른다.
- `constraints`: 정책, 기술, 운영 인력, 일정

모르는 맥락은 묻기 전에 서비스 소개·앱 스토어 설명·리뷰·공개 통계에서 찾는다. 찾지 못하면 `가정`으로 적고 진행하고, 결론을 뒤집을 칸만 한 번에 묻는다. 코드·데이터로 확인할 수 있는 `가정`은 저장소를 보는 사람에게 넘겨 확인한다.

## Evidence Levels

- `observed`: 화면이나 공개 페이지에서 직접 확인
- `reported`: 공식 발표·도움말·기사로 확인했지만 화면은 보지 못함
- `가정`: 근거 없이 둔 값 — 검증 계획에 올린다. 다른 스킬의 보고서와 합칠 때는 `hypothesis`로 읽는다
- `NOT_CHECKED`: 열지 못한 자료 — 내용을 짐작해 쓰지 않는다

## Process

1. 맥락 카드를 쓴다. 사업(단계·규모·사업 방식·가치 약속·운영 역량·콘텐츠 공급), 사용자(타깃·사용 빈도·디지털 숙련도·시력·손의 정밀도·인지 부담·대리 사용), 상황(기기·환경·시간 압박과 감정·함께 쓰는 사람·지역과 문화), 위험(실수 비용·되돌릴 수 있는지·규제·사기 노출과 낯선 사람 간 신뢰·내용 민감도와 재식별) 칸마다 값, 근거, 설계 영향을 적는다. 양식은 [`references/context-card.md`](./references/context-card.md).
2. 결정적 맥락 2~3칸을 고른다. 값을 반대로 뒤집으면 정답이 가장 크게 바뀌는 칸이고, 고른 이유를 한 줄씩 쓴다.
3. 상황·예외 지도를 그린다. 정상 경로와 예외(실패·지연·부족·취소·실수·중복·권한·오프라인·처음과 오랜만·한도·사기 의심·대리 사용)를 결정적 맥락의 세그먼트별로 나누고 빈도 × 실수 비용 × 되돌릴 수 있는지로 순위를 매긴다. 방법은 [`references/exception-map.md`](./references/exception-map.md).
4. 비교 대상 5~8곳(서비스 단위, 한 곳에서 나오는 사례 수는 제한 없음)을 세 겹으로 고른다 — 직접 경쟁, 결정적 맥락이 같은 다른 업종, 위험이 더 크거나 사용자가 더 취약한 극단 사례. 곳마다 겹치는 맥락 칸을 고른 이유로 적는다. 기준은 [`references/comparables.md`](./references/comparables.md), 출발점은 [`references/casebook.md`](./references/casebook.md).
5. 자료를 직접 연다 — 공식 도움말·정책·보도자료·릴리스 노트·디자인과 기술 블로그·앱 스토어 설명·믿을 만한 기사. 출처마다 ID(`S1`…), 주소, 연 날짜를 적는다. 기억만으로 사례를 쓰지 않는다.
6. 사례를 단계 수, 패턴 이름, 기본값, 예외 처리, 핵심 문구로 분해한다. 화면을 베끼지 않는다. 로그인 뒤 화면이 핵심이면 공개 자료로 확인한 단계만 세고 나머지는 「단계 수: 3+ (로그인 뒤 `NOT_CHECKED`)」처럼 적는다.
7. 인사이트 카드를 쓴다 — 무엇을 했나(패턴), 왜 거기서 통했나(그 서비스의 맥락 칸), 대가(포기한 것·부작용·논란), 사실 근거(증거 수준)와 효과 근거(공식 판단·발표 > 유지·확대 이력 > 리뷰 반응 > 추정)를 나눠 적는다. 제재·판결로 문제가 드러난 사례는 반례 카드로 쓴다. 정반대 해법이 둘 다 잘된 경우는 맥락 차이로 설명한다. 양식은 [`references/insight-cards.md`](./references/insight-cards.md).
8. 맥락 거리를 잰다. 인사이트마다 그 서비스와 우리의 결정적 맥락 칸을 대조해 「가져옴 · 바꿔서 가져옴 · 가져오지 않음」과 이유를 쓴다.
9. 제안을 쓴다 — 기본안 하나, 결정적 맥락별 변형, 예외 상태별 처리. 패턴 이름·상태·문구 초안으로 쓰고, 「따라 하면 안 되는 것」과 「작게 먼저 해 볼 것」을 하나 이상씩 붙인다. 단계를 나눠 맡기면 4~8단계 담당은 사례별 「안 맞는 곳」과 반례 카드까지 쓰고, 「따라 하면 안 되는 것」 목록은 9단계 담당이 맥락 거리 표를 보고 확정한다.
10. 검증 계획을 쓴다 — 가장 위험한 가정 3개, 확인 방법, 볼 지표, 제안을 뒤집을 결과.

## Output

1. 맥락 카드와 결정적 맥락
2. 상황·예외 지도: 세그먼트 × 예외, 순위
3. 비교 대상 표: 서비스, 겹(직접 경쟁·같은 맥락·극단), 고른 이유
4. 출처 표: ID, 종류, 제목·주소, 연 날짜, 열람 결과
5. 사례 분해 표
6. 인사이트 카드
7. 맥락 거리 표
8. 제안: 기본안, 맥락별 변형, 예외 상태, 따라 하면 안 되는 것, 작게 먼저 해 볼 것
9. 검증 계획
10. 판정: `READY | NOT_READY | BLOCKED` — READY는 모든 사례가 열어 본 출처로 뒷받침되고, 결정적 맥락별 변형과 예외 처리가 있어 `ux-flow`·`ux-spec`으로 넘길 수 있는 상태

## Hard Gates

| ID  | FAIL 조건                                                        |
| --- | ---------------------------------------------------------------- |
| G1  | 맥락 카드 없이 제안하거나 결정적 맥락을 고르지 않음              |
| G2  | 열지 않은 자료를 인용하거나, 출처 ID도 `가정`도 없는 사례가 있음 |
| G3  | 비교 대상이 한 겹에만 있거나 고른 이유가 없음                    |
| G4  | 인사이트에 「왜 거기서 통했나」나 「대가」가 없음                |
| G5  | 맥락 거리 판단 없이 사례를 그대로 가져옴(화면·문구 복제 포함)    |
| G6  | 결정적 맥락별 변형이나 예외 상태 처리가 없음                     |
| G7  | 제안에 기만 패턴이나 접근성 기준 위반이 있음                     |
| G8  | 검증 계획에 가장 위험한 가정·확인 방법·뒤집을 결과가 없음        |

## Skill Chaining

- 제안의 후보안을 합성 페르소나로 미리 걸러 보기: `ux-simulate`
- 맥락 카드의 `가정`을 실제 사용자로 확인: `ux-research`
- 제안을 흐름과 화면 목록으로: `ux-flow`
- 화면 설계서: `ux-spec`
- 연령·상황별 문구와 어조: `ux-writing`
- 규제와 기만 경계: `ux-dark-patterns`
- 접근성 기준: `ux-a11y`
- 검증 지표와 실험: `ux-metrics`

## Constraints

- 「경쟁사가 하니까」를 근거로 쓰지 않는다.
- 연령·성별·지역을 고정관념으로 쓰지 않는다. 나이는 디지털 숙련도, 시력, 손의 정밀도, 사기 노출처럼 설계에 쓸 수 있는 칸으로 바꿔 쓴다.
- 화면·문구·브랜드 요소를 베끼지 않는다. 흐름과 패턴 수준으로만 가져온다.
- 로그인 벽이나 유료 자료를 우회하지 않는다. 앱 내부 화면은 공개 자료로 확인되는 만큼만 쓴다.
- 사례에 시점을 적는다. 1년 넘은 사례는 지금도 그런지 다시 확인한다.
- 출처 문장을 길게 복사하지 않고 내 말로 요약한다.
- 산출물은 실무에서 쓰는 낱말로 쓴다 — 「꾸리다」는 「구성하다」, 「잣대」는 「기준」(`ux-writing`의 낱말 목록).
