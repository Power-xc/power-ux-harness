# 인사이트 카드

사례에서 가져올 것은 화면이 아니라 이유다. 인사이트 카드는 「무엇을 했나」보다 「왜 거기서 통했나」를 앞에 두고, 그 이유가 우리에게도 있는지 맥락 거리로 따져 가져올지 정한다.

## 인사이트 카드 양식

사례 하나당 카드 하나. 칸을 못 채우면 그 사례는 아직 인사이트가 아니다.

| 칸                 | 내용                                                                                |
| ------------------ | ----------------------------------------------------------------------------------- |
| ID · 서비스 · 시점 | `IN-01`, 서비스 이름, 도입·변경 시점(출처 기준)                                     |
| 무엇을 했나        | 패턴 이름, 기본값, 단계 수, 예외 처리를 흐름 수준으로. 화면·문구 복제 없음          |
| 왜 거기서 통했나   | 그 서비스의 맥락 칸 이름과 값(예: 「실수 비용 높음 · 되돌릴 수 없음」)으로 설명한다 |
| 대가               | 포기한 것, 부작용, 사용자 반발, 운영 비용                                           |
| 사실 근거          | 무엇을 했는지의 증거 수준(`observed`·`reported`·`NOT_CHECKED`)과 출처 ID            |
| 효과 근거          | 통했다는 근거 — 아래 4단계 중 하나와 출처 ID                                        |
| 가져갈 원리        | 다른 서비스로 옮길 수 있는 한 문장(화면 말고 원리)                                  |
| 안 맞는 곳         | 이 원리를 쓰면 안 되는 맥락                                                         |

「왜 거기서 통했나」는 서비스 소개나 기능 설명이 아니다. 맥락 칸의 값으로 말하지 못하면 `hypothesis`로 표시한다.

## 효과 근거

「무엇을 했나」(사실)와 「그래서 통했나」(효과)는 따로 적는다. 정책은 대개 `observed`로 확인되지만 효과는 추정인 경우가 많다. 아래 단계는 효과 근거다.

| 단계 | 강도           | 뜻                                                                                                              | 쓸 때 주의                                               |
| ---- | -------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 1    | 공식 판단·발표 | 서비스나 기관이 변경 결과를 수치나 서술로 밝힘. 규제 기관 제재·법원 판단도 여기 — 무엇이 문제였는지의 공식 판단 | 발표는 자기 홍보일 수 있다 — 측정 방식·기간을 같이 본다  |
| 2    | 유지·확대 이력 | 바꾼 뒤 되돌리지 않고 유지하거나 다른 시장·기능으로 넓힌 것이 정책·릴리스 노트로 확인됨                         | 성과의 간접 증거일 뿐이다 — 다른 이유로 유지했을 수 있다 |
| 3    | 리뷰 반응      | 사용자 리뷰·커뮤니티 반응                                                                                       | 기간·건수·분류 기준을 적는다. 목소리 큰 소수일 수 있다   |
| 4    | 추정           | 위 근거 없이 맥락으로 추론                                                                                      | `hypothesis`로 쓰고 사실처럼 쓰지 않는다                 |

「가져옴」은 사실 근거가 `observed`·`reported`이고 효과 근거가 1\~2단계일 때만 내린다. 효과 근거가 3\~4단계면 「작게 먼저 해 볼 것」으로만 보낸다. 같은 주장에 단계가 다른 근거가 여럿이면 가장 높은 단계를 대표로 쓰되 나머지도 적는다.

## 정반대 해법이 둘 다 맞는 경우

서로 반대인 해법이 각각 잘 통했다면 한쪽이 틀린 것이 아니라 맥락이 다른 것이다. 이때가 맥락 카드를 가장 잘 쓰는 순간이다.

| 칸                 | A 서비스                     | B 서비스         |
| ------------------ | ---------------------------- | ---------------- |
| 같은 문제          | …                            | …                |
| 해법               | …                            | 정반대           |
| 갈라지는 맥락 칸   | 칸 이름: 값                  | 칸 이름: 다른 값 |
| 같은 맥락 칸       | 두 서비스가 공통으로 가진 값 | —                |
| 우리 칸의 값       | …                            | …                |
| 우리에게 가까운 쪽 | A · B · 둘 다 아님           | 이유             |

분석 순서: ① 두 해법이 정말 정반대인지(수준이 같은지) 확인한다. ② 갈라지는 맥락 칸을 찾는다. 후보는 실수 비용, 되돌릴 수 있는지, 사용 빈도, 숙련도, 운영 역량이다. ③ 우리 칸의 값이 어느 쪽에 가까운지 판정한다. ④ 어느 쪽도 아니면 두 해법을 결정적 맥락 세그먼트별 변형으로 나눈다.

예시 (가상): 두 가상 서비스가 같은 「주문 취소」를 반대로 푼다. 서비스 가는 주문 직후 10분간 한 번 눌러 취소되고, 서비스 나는 취소 요청을 받아 사람이 확인한 뒤 처리한다. 가는 상품이 즉시 준비되지 않고 환불이 자동이라 취소 비용이 작다. 나는 주문 즉시 재료가 가공되어 취소가 손실이다. 갈라지는 칸은 R2 되돌릴 수 있는지와 B4 운영 역량이다. 우리 서비스가 가공 전 시간대와 가공 후 시간대를 둔다면 두 방식을 시간대별 변형으로 나눈다.

## 반례 카드

규제 기관 제재·법원 판단·공식 사과로 문제가 드러난 사례는 「가져오지 말 것」의 근거로 쓴다.

| 칸            | 내용                                                       |
| ------------- | ---------------------------------------------------------- |
| 무엇을 했나   | 패턴·기본값을 흐름 수준으로                                |
| 무엇이 터졌나 | 피해·제재·판결의 내용, 기관, 날짜, 출처 ID                 |
| 왜 터졌나     | 맥락 칸 이름과 값(예: 「R5 내용 민감도 높음 · 기본 공개」) |
| 우리의 금지선 | 우리 제안에서 하지 않을 것 한 줄                           |

## 맥락 거리 표

인사이트마다 그 서비스와 우리의 결정적 맥락 칸을 나란히 놓고 거리를 잰다.

| 인사이트 | 결정적 맥락 칸      | 그 서비스 | 우리 | 거리           | 판정                                   | 이유 |
| -------- | ------------------- | --------- | ---- | -------------- | -------------------------------------- | ---- |
| IN-01    | R2 되돌릴 수 있는지 | …         | …    | 가까움·중간·멂 | 가져옴 · 바꿔서 가져옴 · 가져오지 않음 | …    |

인사이트가 많으면 한 줄에 결정적 맥락 칸을 모두 넣는 압축 양식을 써도 된다.

| 인사이트 | R2 (그쪽 → 우리 · 거리) | R4 (…) | R5 (…) | 판정 | 이유 |
| -------- | ----------------------- | ------ | ------ | ---- | ---- |

판정 기준:

| 판정          | 조건                                            | 쓰는 법                                     |
| ------------- | ----------------------------------------------- | ------------------------------------------- |
| 가져옴        | 결정적 맥락 칸이 모두 같거나 우리가 더 취약하다 | 원리와 흐름을 그대로 쓴다(화면은 새로 설계) |
| 바꿔서 가져옴 | 일부 칸이 다르다                                | 다른 칸마다 무엇을 바꿨는지 쓴다            |
| 가져오지 않음 | 통한 이유가 되는 칸이 우리에게 없다             | 이유를 적고, 대신 쓸 해법을 적는다          |

예시 (가상): 인사이트 「송금 직전, 금액 옆에 받는 사람의 이름을 큰 글자로 다시 보여 준다」 (가상의 서비스 가).

| 결정적 맥락 칸      | 서비스 가 | 우리 (가상의 선물 앱)  | 거리 | 판정                                                   |
| ------------------- | --------- | ---------------------- | ---- | ------------------------------------------------------ |
| R1 실수 비용        | 높음      | 낮음(최대 5만 원)      | 멂   | 확인 단계 수는 가져오지 않음                           |
| R2 되돌릴 수 있는지 | 불가      | 보낸 뒤 취소 가능      | 멂   | 보내기 전 확인은 안 가져오고, 보낸 뒤 취소 안내로 바꿈 |
| R4 낯선 사람 신뢰   | 높음      | 높음(처음 보는 수령자) | 같음 | 수령자 이름 재확인은 가져옴                            |

결과: 이름 재확인은 「가져옴」, 확인 단계는 「가져오지 않음」, 취소 방식은 「바꿔서 가져옴」으로 쪼개진다. 한 사례에서 여러 판정이 나오는 것이 정상이다.

## 따라 하면 안 되는 것 점검 질문

제안을 쓰기 전에 사례마다 묻는다. 하나라도 「예」면 「따라 하면 안 되는 것」에 올린다.

1. 이 해법이 통한 이유가 되는 맥락 칸이 우리에게 없는가?
2. 대가(포기한 것)를 우리 사용자가 감당할 수 있는가? 포기한 것이 우리의 가치 약속인가?
3. 규제나 약관이 달라서 그대로 옮기면 안 되는가? (시장·시점이 다른가?)
4. 우리의 사업 방식에서 이 해법이 누구에게 이익이 되는가? 사용자가 아니라 서비스에 이익이면 기만 패턴 점검(`ux-dark-patterns`)으로 보낸다.
5. 운영 인력·기술이 없어서 약속한 처리를 못 지키는가?
6. 접근성 기준(대비·대상 크기·인지 부담)을 어기게 되는가?
7. 사례가 오래됐거나 이후 바뀌었는가?
8. 화면·문구·브랜드를 그대로 가져오게 되는가?

## 작게 먼저 해 볼 것 고르기

가져올 인사이트 중 바로 전체를 만들지 않고 먼저 해 볼 작은 변경을 고른다. 아래 순서로 걸러 한 가지로 좁힌다.

1. 효과 근거 3~4단계(리뷰·추정)이거나 맥락 거리가 「중간」 이상인 것부터 후보로 올린다. 확신이 낮을수록 작게 시작한다.
2. 후보 중 되돌리기 쉬운 것(문구·기본값·순서)을 고른다. 되돌리기 어려운 변경(정책·결제 방식)은 뒤로 미룬다.
3. 영향 범위가 작은 것을 고른다. 한 세그먼트·한 화면·한 예외 상태에 한정되는 변경이 좋다.
4. 한 번에 한 가지만 바꾼다. 둘을 같이 바꾸면 무엇이 효과였는지 알 수 없다.
5. 결과를 볼 지표와 뒤집을 기준을 먼저 쓴다(예: 취소 요청 문의가 늘면 되돌린다).
6. 실제 사용자로 확인할 가정이 있으면 `ux-research`로, 지표 설계는 `ux-metrics`로 넘긴다.
